# Enforce every MCP guarantee on every call

As of October 2026, best practice for publishing a remote MCP server as a SaaS feature reduces to one rule: **the server must enforce every security and governance promise itself, on every request**, because nothing else in the chain can be relied on. The current spec revision, **2026-07-28**, made MCP stateless, and the spec, Anthropic, OpenAI, OWASP and CoSAI all treat the AI client, the model, tool annotations and token scopes as hints rather than controls. For `https://webagent.dev/mcp/<slug>` that translates into five commitments: each slug is its own OAuth 2.1 resource and token audience behind one standards-complete, multi-tenant authorization server; each request gets a fresh, stateless server instance whose tenant context comes only from the verified token; the shipped Support knowledge base template, which already combines untrusted customer-written tickets, private account data and a ticket write path (the "lethal trifecta" behind the Atlassian and Supabase MCP incidents), is broken up by design rather than defended with filters; the draft's "most specific rule wins" resolver gives way to default-deny grants capped by non-overridable ceilings, intersected with the user's own source permissions and with mandatory company scoping for external audiences; and every publish becomes an immutable, hashed, reviewed manifest with tiered kill switches and an append-only audit trail. These failure modes have already produced real breaches: one MCP bug at Asana exposed data across organizations for roughly 1,000 customers ([The Register](https://theregister.com/2025/06/18/asana_mcp_server_bug/)), and a TypeScript SDK flaw leaked responses between clients that shared a server instance ([OSV CVE-2026-25536](https://osv.dev/vulnerability/CVE-2026-25536)). Two load-bearing assumptions remain unverified and must be tested before the ADR commits: whether Claude and ChatGPT honor server-initiated elicitation from remote connectors, and which protocol versions those clients send today.

## Each slug is its own OAuth audience behind one authorization server

The 2026-07-28 spec treats a protected MCP server purely as an **OAuth 2.1 resource server**. The server MUST publish RFC 9728 Protected Resource Metadata (PRM); clients MUST send an RFC 8707 `resource` parameter naming the server's canonical URI in both the authorization and token requests and MUST use PKCE with S256; and the server MUST validate that each token was minted for it, because "MCP servers MUST only accept tokens that are valid for use with their own resources. MCP servers MUST NOT accept or transit any other tokens" ([MCP Authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization)). Tokens travel only in the `Authorization: Bearer` header, never in a query string. The revision also adds RFC 9207 issuer validation against mix-up attacks, formally **deprecates Dynamic Client Registration (DCR)** in favor of Client ID Metadata Documents (CIMD), and adopts a feature-lifecycle policy with a minimum twelve-month deprecation window ([MCP 2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). One dating caveat: the 28 July final-release date rests on search snippets of the MCP blog, and one secondary source still calls the revision a release candidate, but every `/latest/` spec page now resolves to 2026-07-28 content.

The spec explicitly allows a path component to identify an individual server, and PRM discovery inserts that path after the well-known segment, so `https://webagent.dev/mcp/<slug>` maps to `https://webagent.dev/.well-known/oauth-protected-resource/mcp/<slug>` ([Authorization Server Discovery](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery)). Claude requires the PRM `resource` to equal "the URL as the user enters it in Claude, including any path component" and calls a `resource_metadata` pointer in the 401 challenge "the most reliable path on serverless or edge platforms" ([Claude: Authentication](https://claude.com/docs/connectors/building/authentication.md)). Binding the token audience to the exact slug URL gives **per-server isolation**: a token minted for one tenant's server cannot be replayed against another tenant's slug, a boundary a per-tenant audience would erase. The corollary is that a slug is an identity, not a label. Renaming it invalidates every issued token and every customer's connector configuration, so slugs should be immutable once published and retired slugs reserved permanently; the draft validator (`slugProblem` in `src/lib/mcp-server.ts`) checks format and collisions against a static list but has no notion of reserved or retired slugs.

### A single webagent authorization server federates to every customer's identity provider

The spec leaves the authorization server (AS) "hosted with the resource server or a separate entity", and treats the 2025-03-26 design, in which the MCP server doubled as its own AS with default `/authorize` and `/token` endpoints, as legacy ([MCP Authorization 2025-03-26](https://modelcontextprotocol.io/specification/2025-03-26/basic/authorization)). Two client behaviors settle the architecture. OpenAI "strongly recommend[s]" an established identity provider ([OpenAI Apps SDK: Auth](https://developers.openai.com/apps-sdk/build/auth)), and Claude reads only the first entry in `authorization_servers` and "doesn't fall back to later entries" ([Claude: Authentication](https://claude.com/docs/connectors/building/authentication.md)). Together they point to **one webagent-operated or hosted multi-tenant AS** that issues tokens for every slug, federates upstream over OIDC or SAML to each client's, partner's and reseller's IdP, and stamps webagent's own user and tenant identifiers into the tokens. Making a customer's IdP the AS for a slug cannot serve four audiences drawn from many IdPs, and with Entra as the AS every MCP URL would also need registering as an Application ID URI on a verified domain or sign-in fails with `AADSTS9010010` (same source). On the Next.js stack, Vercel's `mcp-handler` covers only the resource-server half, verifying bearer tokens and serving RFC 9728 challenges, and states plainly that "CIMD support is advertised and implemented by your authorization server" ([vercel/mcp-handler](https://github.com/vercel/mcp-handler)). Vendor support for CIMD and enterprise grants is uneven (Auth0 lists Cross App Access as Early Access), and this research did not verify current matrices for WorkOS, Stytch, Descope, Auth0 or Clerk, so that support belongs on the selection checklist.

Client registration follows a fixed priority: pre-registered credentials, then CIMD, then deprecated DCR, then manual entry ([Client Registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)). DCR's cost is sprawl and skipped consent. Claude "register[s] a new client on every fresh connection, which can result in very large numbers of registered clients" ([Claude: Authentication](https://claude.com/docs/connectors/building/authentication.md)), and Cloudflare warns that DCR without an approval step lets any client self-register ([Cloudflare: MCP Authorization](https://developers.cloudflare.com/agents/model-context-protocol/authorization/)). CIMD trades those risks for two others. The AS fetches a URL supplied by an unknown client, an SSRF vector that calls for blocking private and cloud-metadata ranges, routing fetches through an egress proxy and avoiding hand-rolled IP checks because "attackers exploit encoding tricks"; and a metadata document cannot prove which local process owns a localhost redirect, so the consent screen must display client hostnames prominently and the AS may apply domain trust policies by allowlist, reputation or domain age ([Security Best Practices](https://modelcontextprotocol.io/specification/latest/basic/security_best_practices)). That domain allowlist doubles as a governance control: it lets an admin decide **which AI clients may connect to a given slug**, which is the only lever web-agent has over whose retention terms its data lands under.

In practice the webagent AS should advertise CIMD together with `none` client authentication, list S256, emit `iss` with `authorization_response_iss_parameter_supported: true` (which also unlocks ChatGPT's fixed redirect URI), accept form-encoded token requests, return `invalid_grant` for dead refresh tokens, answer within ten seconds, and keep its well-known endpoints reachable from vendor egress ranges, since "a WAF in front of your identity provider can break the flow" ([Claude: Authentication](https://claude.com/docs/connectors/building/authentication.md)). A search snippet of Anthropic's help center says the callback "may move to `https://claude.com/api/mcp/auth_callback`"; the claim was absent from the fetched documentation, but registering both URIs costs nothing ([Claude Help](https://support.claude.com/en/articles/11503834)). Neither client supports machine-to-machine `client_credentials`, which suits a per-user OAuth design. Claude's beta `static_headers` mode should not be offered at all: Anthropic describes that credential as "the organization's credential, not a person's" (same source), and a shared credential erases the per-user identity on which every downstream permission, audit and revocation control depends.

### Enterprise-managed authorization removes consent screens for staff and large partners

The MCP **Enterprise-Managed Authorization (EMA)** extension, listed as Stable for 2026-07-28, lets a client exchange the user's enterprise SSO assertion for an **Identity Assertion JWT Authorization Grant (ID-JAG)** through RFC 8693 token exchange at the IdP, then present it to the MCP server's AS with the RFC 7523 JWT-bearer grant; the resulting access token "MUST be audience-restricted to the MCP Server" ([ext-auth EMA spec](https://raw.githubusercontent.com/modelcontextprotocol/ext-auth/main/specification/stable/enterprise-managed-authorization/2026-07-28/enterprise-managed-authorization.mdx)). In June 2026 the MCP blog reported Okta as the first supported IdP, Anthropic's implementation across Claude, Claude Code and Cowork, and VS Code support in preview; ChatGPT was not mentioned, and OpenAI's own auth documentation rules out JWT-bearer grants ([MCP blog: Enterprise-Managed Auth](https://blog.modelcontextprotocol.io/posts/enterprise-managed-auth/)). Claude's requirements are specific: a Team or Enterprise plan, no DCR, the JWT-bearer grant listed in `grant_types_supported`, and "an explicit allowlist of trusted issuer URLs per tenant" with unlisted issuers rejected as `invalid_grant`. Because Claude silently mints fresh ID-JAGs from the IdP refresh token, "a short lifetime, such as one hour, doesn't force users to repeat single sign-on" ([Claude: Enterprise Managed Auth](https://claude.com/docs/connectors/building/enterprise-managed-auth.md)). The extension spec and Claude disagree on discovery (the spec advertises support through `authorization_grant_profiles_supported`, Claude reads `grant_types_supported`), so the AS should advertise both. EMA is the natural path for Internal staff through webagent's own IdP and for large partners willing to register their issuer; smaller clients and resellers will use the interactive flow.

### Identities and directory attributes come from a governed directory, not convenience claims

External identities should be keyed on the upstream `(iss, sub)` pair, or Entra's `tid` plus `oid`, never on email or UPN; Microsoft says email "isn't guaranteed to be correct, and is mutable over time - never use it for authorization" ([Entra optional claims](https://learn.microsoft.com/en-us/entra/identity-platform/optional-claims-reference)). A verified email domain is useful only as a routing hint for which tenant to send someone to. Business unit and department, the two dimensions the access rules depend on, do not appear in default IdP tokens: Entra's default optional claims omit `department` and require extension attributes (same source), while the SCIM 2.0 Enterprise User extension carries `department`, `division`, `organization`, `costCenter` and `manager` ([RFC 7643 §4.3](https://datatracker.ietf.org/doc/html/rfc7643#section-4.3)). The robust design is a webagent-side directory record populated by SCIM provisioning or per-tenant claim mapping and read at request time. The draft instead models a person "as their directory profile describes them at sign-in", so someone who changes department keeps the old department's access until a token is reissued.

Scopes should be coarse and minimal, with the fine-grained matrix evaluated on the server. The spec describes `scopes_supported` as "the minimal set of scopes necessary for basic functionality", expects step-up through a `403` carrying `error="insufficient_scope"` with every needed scope in a single challenge, and names as common mistakes publishing every scope, omnibus scopes, and "treating claimed scopes in token as sufficient without server-side authorization logic" ([MCP Authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization); [Security Best Practices](https://modelcontextprotocol.io/specification/latest/basic/security_best_practices)). Mapping Read, Write and Manage to separate scopes means a stolen read token can never write, while the dataset-by-audience-by-unit-by-department decision still runs on every call. The AS SHOULD issue short-lived access tokens and MUST rotate refresh tokens for public clients ([Security Considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)), and Claude registers as a public client that refreshes up to five minutes before expiry ([Claude: Authentication](https://claude.com/docs/connectors/building/authentication.md)). The MCP spec defines no revocation mechanism, so the answer is standard OAuth revocation plus per-request policy evaluation: an admin removing a dataset from a rule should take effect on the next call, not at token expiry. OpenAI sets the floor, telling servers to verify signature, `iss`, `exp`/`nbf`, `aud`/`resource` and scopes "on every request" ([OpenAI Apps SDK: Auth](https://developers.openai.com/apps-sdk/build/auth)).

## Statelessness ends session hijacking and moves tenant isolation into application code

The 2026-07-28 revision removed `Mcp-Session-Id`, the `initialize` handshake, the GET SSE stream and SSE resumability. MCP is now "a stateless protocol: all the information needed to process a request is contained in the request itself", and servers MUST NOT rely on prior requests to establish capabilities, protocol version or client identity ([Base Protocol](https://modelcontextprotocol.io/specification/2026-07-28/basic/index)); `server/discover` became mandatory and `subscriptions/listen` replaced the GET stream ([changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). The security payoff is that 2025-era session attacks, such as "Session Hijack Prompt Injection" through a shared event queue keyed by session ID, disappear at the transport layer ([Security Best Practices 2025-11-25](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices)). Their replacement is **state-handle hijacking**: servers "MUST NOT treat possession of a state handle as authentication" and SHOULD bind each handle server-side as `<user_id>:<handle>` ([Security Best Practices](https://modelcontextprotocol.io/specification/latest/basic/security_best_practices)). For web-agent, every draft ID, pagination cursor and task ID should be keyed to tenant, user and server and re-authorized on each use, because "a handle is a name, not a capability" ([MCP Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)). The `requestState` blob that round-trips through the client during multi-round-trip requests is untrusted input; the spec shows it as an opaque string without mandating integrity protection, so web-agent should sign or encrypt it whenever it carries anything the server relies on. One draft detail is already stale: `toClientView` describes server instructions as arriving "from initialize", a handshake the current spec no longer has.

### Four transport checks are mandatory rather than optional

Origin validation is a MUST, with a 403 for any present-but-invalid `Origin` header ([Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)). Hosted clients call from vendor backends and usually send no Origin, so the workable rule is to allowlist known browser origins (the web-agent app, and MCP Inspector in development), reject everything else, and never pair `Access-Control-Allow-Origin: *` with credentials. The revision also mirrors parts of the body into headers: every POST carries `MCP-Protocol-Version` and `Mcp-Method`, `tools/call` adds `Mcp-Name`, and servers MUST reject any header-body disagreement with a 400 `HeaderMismatch` (-32020), because a load balancer could otherwise route or rate-limit on a benign header while the server executes a harmful body (same source). If a WAF or edge limiter keys on `Mcp-Name`, the origin must still enforce the match, and sensitive parameters must never be marked `x-mcp-header`, since header values are visible to intermediaries ([MCP Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)). `clientInfo` is self-reported and "SHOULD NOT" drive security decisions ([Base Protocol](https://modelcontextprotocol.io/specification/2026-07-28/basic/index)). Finally, closing the SSE response stream "MUST be treated by the server as cancellation of that request", so tool handlers should honor the request's abort signal. Because the spec also dropped redelivery and clients re-issue a broken request under a new ID, side-effecting tools such as `create_ticket` and `send_email` need server-side idempotency keys. Older 2025-era clients can be served through a stateless fallback that answers GET and DELETE with 405 and never mints or echoes session IDs, while HTTP+SSE is formally Deprecated and eligible for removal ([Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)). This research did not confirm which protocol versions Claude and ChatGPT send today, which leaves the fallback's lifespan open.

### Cross-tenant isolation is where real failures have happened

The documented multi-tenant failures came from application logic, not transport. **CVE-2026-25536** leaked responses across clients in the TypeScript SDK when one `McpServer` or transport instance was reused, "most commonly in stateless `StreamableHTTPServerTransport` deployments", rated CVSS 7.1 and fixed in 1.26.0 ([OSV](https://osv.dev/vulnerability/CVE-2026-25536)). In **June 2025 Asana** found a bug that exposed data to other organizations' MCP users and took its server offline from June 5 to 17 ([BleepingComputer](https://bleepingcomputer.com/news/security/asana-warns-mcp-ai-feature-exposed-customer-data-to-other-orgs/)). Vercel's Fluid compute runs multiple invocations inside the same function instance ([Vercel: Deploy MCP servers](https://vercel.com/docs/mcp/deploy-mcp-servers-to-vercel)), which turns any module-level cache, singleton or in-memory map into a latent cross-tenant leak. The rules follow directly. Construct the MCP server per request and pin the SDK at 1.26.0 or later (or v2), which also covers the DNS-rebinding fix for CVE-2025-66414 ([VulnerableMCP](https://vulnerablemcp.info/vuln/cve-2025-66414-66416-dns-rebinding-mcp-sdks.html)). Resolve the slug against the server registry on every request and return 404 for unknown or disabled slugs before any auth work. Derive tenant, server, user and scopes only from the verified token plus the registry, and ignore any tenant or company ID that arrives as a tool argument. The spec lets `tools/list` "vary by the authorization presented on the request" while forbidding variation per connection ([MCP Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)), and caller-specific lists should carry `cacheScope: "private"` so shared intermediaries never cache them across tenants ([changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). Tenant scoping must then be enforced a second time in the database, as the data-governance section below describes.

### Server-held credentials and hard limits contain the blast radius

Platform keys, such as the web search and email provider keys, belong in server-side secret storage, injected at call time and never present in schemas, structured results, `_meta`, error text or telemetry attributes. Shared keys create a confused-deputy problem, because any tenant's caller can make web-agent's own identity act, so the server must constrain arguments itself (limiting `send_email`'s sender to tenant-verified domains and capping recipients), meter per-tenant quotas, use provider sub-accounts where available so abuse is attributable and revocable, and audit every downstream call against tenant, user and OAuth client. If web-agent ever lets tenants connect their own third-party accounts through a static web-agent OAuth client, it becomes the spec's "MCP proxy server", and the per-client consent MUSTs apply: a per-user registry of approved client IDs, a consent screen naming the client, scopes and redirect URI, signed `__Host-` cookies, exact redirect matching and single-use `state` ([Security Best Practices](https://modelcontextprotocol.io/specification/latest/basic/security_best_practices)).

The spec makes four server duties mandatory ("Validate all tool inputs; Implement proper access controls; Rate limit tool invocations; Sanitize tool outputs") ([MCP Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)), and 2026-07-28 hardens schemas further: implementations MUST NOT auto-dereference network `$ref` values and SHOULD bound composition depth and subschema counts so a schema cannot become a denial-of-service vector against the validator ([Base Protocol](https://modelcontextprotocol.io/specification/2026-07-28/basic/index)). Concrete numbers are left to implementers, so the ADR should fix them: a body cap of around 1 MB checked before parsing, strict validators with `additionalProperties: false` and explicit `maxLength` and `maxItems`, per-tool deadlines of 10 to 30 seconds for synchronous tools, database statement timeouts, and capped, paginated results. Protocol errors should be generic and carry a correlation ID, while `isError` tool errors should be model-actionable but sanitized and drawn from fixed templates. Rate limiting needs two layers, because Vercel WAF counters are kept per region and "traffic matching a given rate limit key in multiple regions can exceed the limit you configure" ([Vercel WAF Rate Limiting](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting)): the edge absorbs volumetric abuse by IP or JA4 fingerprint, and authoritative limits live in a global application store keyed by tenant, user, OAuth client and tool, weighted for expensive tools and answered with 429 plus `Retry-After`. Bot challenges must stay off the MCP route, because MCP clients are not browsers. Per-server IP allowlists can be an enterprise option, but they must list vendor egress ranges rather than office IPs and never replace OAuth; a secondary source also reports that Claude connectors are IPv4-only ([Zuplo](https://zuplo.com/learn/mcp/errors/mcp-server-works-in-claude-code-but-not-claude-ai)).

On hosting, `mcp-handler` 2.x runs on SDK v2, serves 2026-07-28 natively, is stateless, has removed HTTP+SSE and notes "Redis is no longer needed or used", but its README is silent on Origin validation, so that check must be added explicitly ([vercel/mcp-handler](https://github.com/vercel/mcp-handler)). Vercel functions default to 300 seconds and allow up to 800 on Pro and Enterprise ([Vercel: Max duration](https://vercel.com/docs/functions/configuring-functions/duration)); setting each route's `maxDuration` near the slowest synchronous tool, not the plan maximum, bounds the cost of a runaway call. Work beyond about 30 seconds belongs in the stable **Tasks extension** (`io.modelcontextprotocol/tasks`), where the task "must be durably created before sending the response" and servers must "never return a task to a client that did not declare support" ([MCP Tasks](https://modelcontextprotocol.io/extensions/tasks/overview)), backed by Vercel Workflows, with every `tasks/get` re-checking that the caller owns the task. An external gateway such as APIM or Kong is optional, because web-agent already is that gateway: it owns the tool allowlists, the credentials and the tenant routing.

## The Support KB template already assembles a lethal trifecta

The dominant AI-specific threat to this server is indirect prompt injection carried in data a tool returns, and it cannot be patched because it is not a code bug. Simon Willison's "lethal trifecta" names the dangerous condition (access to private data, exposure to untrusted content and the ability to communicate externally) and argues that guardrail products cannot be relied on because "in web application security 95% is very much a failing grade" ([Willison](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). Meta's "Agents Rule of Two" turns that into a design rule: until injection can be detected reliably, a session should combine no more than two of the three, and an agent that needs all three "should not be permitted to operate autonomously" ([Meta AI](https://ai.meta.com/blog/practical-ai-agent-security/)). The MCP maintainers add that a tool's risk "depends on what else is in the session", so no single tool's annotations capture it ([MCP blog: Tool Annotations](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/)). The guidance base is now dense, spanning OWASP's MCP Top 10 (beta), CoSAI's January 2026 taxonomy of roughly 40 MCP threats and an NSA information sheet from May 2026, and none of it claims prompt injection is solved ([OWASP MCP Top 10](https://owasp.org/www-project-mcp-top-10/); [CoSAI](https://www.coalitionforsecureai.org/wp-content/uploads/2026/03/model-context-protocol-security-1.pdf); [NSA](https://www.nsa.gov/Press-Room/Press-Releases-Statements/Press-Release-View/Article/4496698/)).

### Customer-written tickets plus a write-back path reproduce the Atlassian attack

The closest precedent is Cato CTRL's June 2025 attack on Atlassian Jira Service Management: an outside user filed a malicious ticket, a support engineer ran an MCP action on it, the injected instructions executed with the engineer's internal permissions, and internal data was written back into the ticket where the attacker could read it ([Cato Networks](https://www.catonetworks.com/blog/cato-ctrl-poc-attack-targeting-atlassians-mcp/)). Supabase repeated the shape a month later. An attacker's support ticket told a Cursor agent to read `integration_tokens` and post them into the ticket thread, and because the MCP connection ran as `service_role`, row-level security never applied; the researchers' verdict was that "No permissions were violated. The agent just followed instructions it should never have trusted" ([General Analysis](https://www.generalanalysis.com/blog/supabase-mcp-blog)). Supabase's response (read-only mode, project scoping and warning wrappers around results) "reduced risk but did not eliminate it" ([Supabase](https://supabase.com/blog/mcp)). In 2026, Sentry "agentjacking" used public, write-only DSNs to post fake error events carrying "remediation" instructions, achieving **85% exploitation success** against at least 2,388 organizations with injectable DSNs, and Sentry declined a root-cause fix as "technically not defensible" ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-agentjacking-mcp-sentry-injection-20260612/)). Rendered output is the other exit: ForcedLeak (CVSS 9.4) smuggled lead emails out through an image URL on an expired allowlisted domain that cost about $5 to buy ([The Hacker News](https://thehackernews.com/2025/09/salesforce-patches-critical-forcedleak.html)), and CamoLeak (CVSS 9.6) encoded private repository data in the order of pre-signed image URLs triggered by hidden markdown comments ([Legit Security](https://legitsecurity.com/blog/camoleak-critical-github-copilot-vulnerability-leaks-private-source-code)).

The draft catalog fits this pattern exactly. The Tickets dataset is described as "Customer conversations, status and internal notes", which puts outsider-authored text beside internal notes; Customer accounts ("Plan, billing status, credits and contacts") are private data; and the Support KB template gives Internal support staff Write on tickets with `update_ticket`. If that tool can post a customer-visible reply, it is the Atlassian exfiltration path nearly verbatim. The general-purpose tools widen the hole. `send_email` and `web_search` touch no datasets, so the draft's `canUseTool` check, which requires enough access on "every dataset the tool touches", passes vacuously for them; because the blank draft also creates an empty rule for all four audiences with the per-tool default, a server that adds `send_email` offers it to Partners and Resellers holding no dataset access at all. A web search is an outbound channel too, since the query string carries whatever the model chooses to put in it.

Microsoft states the right bar: the goal is that "even if some prompt injections are successful, this will not lead to security impacts", because spotlighting and classifiers are "probabilistic" while data-access attacks "can be deterministically mitigated using fine-grained permissions and access controls" ([MSRC](https://www.microsoft.com/en-us/msrc/blog/2025/07/how-microsoft-defends-against-indirect-prompt-injection-attacks)). The controls should therefore change what the server can do. The strongest is a **trifecta check at publish time** that classifies each dataset as trusted-authored, untrusted (customer- or web-sourced) or private, classifies each tool as an outbound channel or not (send email, web search, any URL fetch, any write to a customer-visible field), and warns or blocks whenever a single rule's effective view combines all three; it must run per rule rather than per server, because Partners and Internal escalations see different tool sets. Next, remove the outbound leg where possible by restricting `send_email` recipients to the authenticated user or the company's own domains, offering draft-then-send as Microsoft's own example does, and requiring confirmation for customer-visible ticket replies whenever the same principal can read accounts. Tools must run as the end user with least privilege and never through a service-role credential, the Supabase root cause. Only after those come the probabilistic measures: placing customer-written text in labeled, structured fields with provenance, and stripping markdown images, HTML tags and comments, invisible Unicode and ANSI escapes from untrusted text, in line with OWASP's rule to "treat all tool responses as untrusted, including from approved servers" ([OWASP MCP Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html)). Statelessness limits session "tainting": since `tools/list` cannot change per connection, a rule such as "this user just read untrusted tickets, so confirm the next email" must run at call time, keyed on user and a time window, and only approximates a session because the server never sees the client's conversation boundaries. Nor can the server see other MCP servers the user has connected, so cross-server trifectas remain the client's problem; web-agent's job is to avoid becoming the outbound leg for someone else's data.

### Admin-written descriptions make web-agent a tool-metadata publisher

Tool metadata functions as a prompt. Invariant Labs showed hidden `<IMPORTANT>` blocks in descriptions leaking SSH keys, "rug pulls" that change a description after approval, and cross-server shadowing in which a malicious server's description redirected a trusted `send_email` tool to the attacker without ever being called ([Invariant Labs](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks)). Trail of Bits showed injections fire as soon as `tools/list` loads them, before any call ([Trail of Bits](https://blog.trailofbits.com/2025/04/21/jumping-the-line-how-mcp-servers-can-attack-you-before-you-ever-use-them/)), and CyberArk extended the surface to every schema field and to tool outputs and error strings ([CyberArk](https://www.cyberark.com/resources/threat-research-blog/poison-everywhere-no-output-from-your-mcp-server-is-safe)). Two 2026 papers quantify the problem. Payloads hidden in the Unicode TAG block rendered invisibly in approval dialogs while reaching the model; all 8 techniques delivered, 4 of 8 evaded a string-matching sanitizer, and re-approval was forced in 0 of 8 cases even during a rug pull ([arXiv 2607.05744](https://arxiv.org/abs/2607.05744)). A census of 21,643 registry servers found **40.6% of multi-version servers changed their advertised metadata silently**, with silent drift correlating with high-severity findings at an odds ratio of 2.96 ([arXiv 2609.14119](https://arxiv.org/abs/2609.14119)).

Because web-agent is the trusted publisher, outside poisoning is not its main exposure; its own risks are an admin or compromised admin account writing model-directed instructions into server instructions or tool descriptions, imported templates carrying hidden characters, and definitions changing after customers approved them. The response is to lint every model-readable field (names, titles, descriptions, parameter names and descriptions, defaults, enums and server instructions), rejecting invisible and control Unicode, references to other tools or servers and imperative instructions to the model, and enforcing length caps. Those rules mirror Anthropic's Software Directory Policy, which demands "narrow and unambiguous" descriptions, forbids coercing calls to other software or pulling instructions from external sources, and says software "must not contain hidden, obfuscated, or encoded instructions" ([Anthropic Software Directory Policy](https://support.claude.com/en/articles/13145358)), as well as OpenAI's ban on metadata that steers model preference or conceals behavior ([OpenAI App submission guidelines](https://developers.openai.com/apps-sdk/app-submission-guidelines)), which keeps published servers eligible for directory listing. The draft's `checkServer` currently checks only that instructions exist and exceed 80 characters. The full definition must be hashed, not just its description, because "a flipped readOnlyHint or destructiveHint can change client approval behavior without any visible description change" ([OWASP MCP Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html)). Tool names should carry a short server prefix within the 64-character cap of Anthropic's directory ([Claude review criteria](https://claude.com/docs/connectors/building/review-criteria.md)), catch-all tools such as raw SQL or a generic `api_request` should be banned (Claude's review rejects any tool that mixes safe and unsafe methods), and errors should come from fixed templates so untrusted content never echoes through error strings.

### Annotations steer client prompts, but only the server can guarantee a confirmation

The spec says clients "MUST consider tool annotations to be untrusted unless they come from trusted servers" ([MCP Tools](https://modelcontextprotocol.io/specification/latest/server/tools)), yet the clients that matter act on them. Claude runs `readOnlyHint: true` tools without per-call confirmation and always prompts for `destructiveHint: true` ([Claude review criteria](https://claude.com/docs/connectors/building/review-criteria.md)), and Team and Enterprise Owners can set connector tool categories to Always allow, Needs approval or Blocked ([Claude Help](https://support.claude.com/en/articles/11176164)). According to the indexed text of OpenAI's developer-mode guide, ChatGPT treats any tool lacking the read-only hint as a write that needs confirmation ([OpenAI developer mode](https://developers.openai.com/api/docs/guides/developer-mode)). OpenAI's submission rules require all three hints as explicit booleans, mark deletion, overwriting, cancellation and irreversible sends as destructive, insist that "being able to undo an action does not, by itself, justify setting `destructiveHint` to `false`", and set `openWorldHint` true "for public or open-ended entities, including read-only web search" ([OpenAI App submission guidelines](https://developers.openai.com/apps-sdk/app-submission-guidelines)). The draft's `annotations()` sets only `readOnlyHint` on read tools and never sets `openWorldHint`, which defaults to the worst case of `true` ([MCP blog: Tool Annotations](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/)), so its closed-domain dataset tools advertise themselves as open-world.

| Catalog tool (draft safety label) | `readOnlyHint` | `destructiveHint` | `openWorldHint` | What the server must enforce |
|---|---|---|---|---|
| `search_help_center`, `get_ticket`, `lookup_account` (read) | true | false | false | Read-only credentials, field allowlist, company scoping |
| `web_search` (read) | true | false | true | Counted as an outbound channel in the trifecta check |
| `create_ticket` (write) | false | false | false | Idempotency key, per-tool rate limit |
| `update_ticket` (write) | false | true if it overwrites customer-visible content | false | Confirmation when the same person can read accounts |
| `send_email` (write) | false | true (irreversible send) | true | Recipient allowlist or draft-then-send, server-side confirmation |
| `delete_ticket`, `issue_credit` (destructive) | false | true | false | Server-enforced confirmation, per-call caps |

Confirmation has to be enforced by the server because client prompts are easy to bypass. In Claude's Research mode, "Claude can invoke tools from your connectors automatically without further approval" ([Claude Help: custom connectors](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)); ChatGPT workspace admins can choose "Never ask" ([Strac](https://www.strac.io/blog/chatgpt-connectors)); and CoSAI notes that hosts "allow users to disable the confirmation prompt" and recommends "elicitation on the MCP server side" ([CoSAI](https://www.coalitionforsecureai.org/wp-content/uploads/2026/03/model-context-protocol-security-1.pdf)). Two catalog tools need special care: `issue_credit` moves money, and Anthropic's policy does not support autonomous financial transactions without a human in the loop ([Anthropic Software Directory Policy](https://support.claude.com/en/articles/13145358)), while `send_email` is labeled only "write" even though Claude guarantees a prompt only for destructive tools, which is why the table marks it destructive. Under 2026-07-28 a server elicits input by answering `tools/call` with an `InputRequiredResult`. URL mode is the strongest form, because data never passes through the client, the server "MUST NOT provide a URL which is pre-authenticated", and it must verify that the person opening the URL is the token's user; form mode is weaker, since a buggy or malicious client could auto-accept ([MCP Elicitation](https://modelcontextprotocol.io/specification/latest/client/elicitation)). The right pattern is a URL-mode confirmation page on `webagent.dev` showing the exact action and parameters, form mode as a fallback, and, for clients that declare no elicitation support, a refusal with an actionable `isError` or a queued approval inside the web-agent app. The draft's "Confirm first" setting (`confirmToolIds`) is the right instinct but remains a hint until enforced this way, and its lint nudges only destructive tools, so `send_email` never triggers it. The largest open question in this report is whether claude.ai, Claude Desktop and ChatGPT actually support form- or URL-mode elicitation and the `InputRequiredResult` flow from remote connectors, which must be tested before the design depends on it. Server-side sampling should stay out of v1, given the resource-theft and conversation-hijacking attacks Unit 42 documented through that channel ([Unit 42](https://unit42.paloaltonetworks.com/model-context-protocol-attack-vectors/)).

## Default-deny grants with hard ceilings beat most-specific-wins

### The draft resolver silently drops grants and lets narrow rules override org-wide intent

`matchRule()` filters rules by audience, business unit and department, sorts them by specificity and takes the first match, and `accessFor()` then reads only that rule's map, resolving any unlisted dataset to `"none"`. That creates three hazards. A narrower rule quietly removes access: if an admin adds a Tier 2 department rule to the Support KB template that grants Manage on tickets and lists nothing else, Tier 2 staff silently lose the help-center Write, runbooks Read and accounts Read the Customer Support unit rule gave them. A narrower rule can also widen access beyond org-wide intent, since an audience-wide "Partners: none on accounts" yields to any department-level Partner rule, and there is no way to say "never" across an audience. And ties at equal specificity resolve by array order. No established engine works this way. Cedar denies by default, lets any satisfied `forbid` override every `permit`, produces order-independent outcomes and returns the "determining policies" behind each decision ([Cedar](https://docs.cedarpolicy.com/auth/authorization.html)), while PostgreSQL combines permissive row-security policies with OR and restrictive ones with AND, and a table with RLS enabled but no policies shows nothing ([PostgreSQL](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)).

The recommended resolution borrows those semantics: deny by default, set each dataset's effective level to the **maximum across all matching grants**, cap it with **non-overridable ceilings and forbids** in which deny always wins (external audiences never hold Manage, Partners never see billing fields, external audiences are always company-scoped on tickets and accounts), and log the determining rules for every decision. Adding a grant can then never reduce access and adding a forbid can never increase it, which makes outcomes predictable to admins. Exceptions such as "department X gets less" become explicit scoped forbids instead of specificity shadowing, and logged decisions let the product replay a proposed rule change before publishing to show exactly who would gain or lose access.

### Audiences are attributes, but company tenancy is a relationship

Audience, business unit and department are attributes and fit attribute-based control. Record-level tenancy is relational: a client sees its own company's tickets, a reseller sees the accounts of customers it resold to, and a partner sees co-sold accounts. The draft's `companyScopedIds` is a single switch ("only see their own company's records") that cannot express reseller-of or partner-of relationships; in the Support KB template, Resellers get Read on company-scoped accounts, which as written shows each reseller its own account rather than the customers it serves. A relationship store (OpenFGA, SpiceDB or Postgres relationship tables) fits, and Google's Zanzibar demonstrates the model at a scale of trillions of access-control entries ([Zanzibar](https://www.usenix.org/conference/atc19/presentation/pang)). OpenFGA documents the search trade-offs: search-then-check suits small result sets, listing accessible IDs before searching becomes impractical beyond roughly 1,000 objects, and a local permission index "can lag behind recent revocations" and so needs a final check before returning results ([OpenFGA](https://openfga.dev/docs/interacting/search-with-permissions)). Whatever the pattern, filtering must precede ranking, snippets, counts and embedding search, because filtering afterward still leaks titles and counts. The policy decision point should run twice, at `tools/list` to hide unusable tools and again on every `tools/call`, as in Cerbos's MCP pattern, which logs principal, attributes, action, resource, policy and outcome ([Cerbos](https://www.cerbos.dev/blog/mcp-authorization)). Hiding a tool improves the experience but enforces nothing.

### Effective access is policy intersected with the user's own permissions

The market standard is that AI sees only what the user already can. Microsoft Copilot "only surfaces organizational data to which individual users have at least view permissions" ([Microsoft Learn](https://learn.microsoft.com/en-us/copilot/microsoft-365/microsoft-365-copilot-privacy)), and OpenAI says ChatGPT connectors respect existing permissions and that app permissions "don't add access" ([Apps in ChatGPT](https://help.openai.com/en/articles/11487775-apps-in-chatgpt)). A service-account design, in which web-agent reads broadly and filters with its own rules, creates a parallel permission system that drifts whenever the source revokes access, someone changes department, or the source holds record-level permissions (private tickets, restricted runbooks) that dataset-level rules cannot see. The safe formula is **effective access = web-agent policy ∩ the user's source permissions ∩ token scopes**, with web-agent's rules presented to admins as a ceiling on what AI clients may reach rather than a grant system; because mirroring also copies existing oversharing, sensitivity ceilings stay in force even where the source would allow access. External users usually have no identity in internal source systems, so their company must come from an authoritative mapping (verified domain, IdP organization claim, CRM contact-to-account link), never from their own input, and that relationship graph, effectively the access list for externals, needs a named owner and periodic review. Help-center and release-notes content can be read by a service account under server policy, whereas tickets and accounts hold third parties' personal data and warrant delegated or source-synced permissions.

Tenant scoping must also hold in the database. In PostgreSQL, superusers and `BYPASSRLS` roles always bypass row security, table owners bypass it unless the table is set to `FORCE ROW LEVEL SECURITY`, and referential-integrity checks always bypass it, creating a covert channel ([PostgreSQL](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)). The MCP runtime role therefore must be neither owner, superuser nor `BYPASSRLS`, company scoping should be a restrictive policy keyed to a per-request setting, and with pooled serverless connections that setting belongs inside a transaction (`SET LOCAL`) so it cannot leak into the next request. Field-level control should work as an allowlist through a per-tool, per-audience `outputSchema`, so that ticket "internal notes" never reach external audiences, contact and billing details are masked, and end-customer conversation bodies are withheld from Partners and Resellers by default. Redaction is the server's job; a third-party guide notes that ChatGPT's admin controls "don't inspect the data an app returns" ([CData](https://www.cdata.com/blog/chatgpt-enterprise-connectors-guide)).

### Every result leaves the trust boundary under the connecting user's AI plan

Once a tool result is returned, it lives under the connecting user's AI plan, not web-agent's. Anthropic's commercial products do not train on inputs or outputs by default, and although feedback can retain a conversation for up to five years, it "does not include raw content from connectors" unless that content was copied into the chat ([Anthropic Privacy Center](https://privacy.claude.com/en/articles/7996868-is-my-data-used-for-model-training)); API data is deleted within 30 days ([Anthropic retention](https://privacy.claude.com/en/articles/7996866-how-long-do-you-store-my-organization-s-data)). Anthropic consumer users who opt in have their data retained for **five years** and used for training ([Anthropic consumer terms](https://www.anthropic.com/news/updates-to-our-consumer-terms)), and OpenAI's Free, Plus, Go and Pro plans "may use information accessed from apps to train" when "Improve the model for everyone" is on, unlike Business, Enterprise and Edu ([Apps in ChatGPT](https://help.openai.com/en/articles/11487775-apps-in-chatgpt)). A single news report adds that Anthropic introduced mandatory 30-day safety retention for its most advanced models in June 2026 before offering enterprise safeguards in September ([PYMNTS](https://www.pymnts.com/?p=4144828)). Web-agent cannot see the client's plan, so a partner on a personal consumer account could put a company's customer data into a training corpus. The available mitigations are a per-server allowlist of approved AI clients enforced through the CIMD domain policy, contract terms requiring external audiences to use business-tier AI with training disabled, stricter minimization for externals, and a consent screen stating that results go to the user's AI provider under their own agreement. Residency guarantees also end at the MCP response: Microsoft notes that Anthropic models are excluded from its EU Data Boundary ([Microsoft Learn](https://learn.microsoft.com/en-us/copilot/microsoft-365/microsoft-365-copilot-privacy)), proof that where an LLM processes data can differ from where it is stored.

### Opening a server to external audiences is a disclosure decision

Under GDPR the data-owning company is the controller and web-agent its processor, while the AI provider is chosen by whichever organization connects and is that organization's processor, not web-agent's sub-processor. The exception is any tool where web-agent calls an LLM itself; the catalog's `translate_text` and `analyze_sentiment` likely do, which would put that provider on web-agent's own sub-processor list. Exposing tickets containing end-customer data to Partners or Resellers is a disclosure that needs a lawful basis, and combined with LLM processing it makes a DPIA likely, for which the EDPB expert report on LLM privacy risks offers a usable method ([EDPB](https://www.edpb.europa.eu/our-work-tools/our-documents/support-pool-experts-projects/ai-privacy-risks-mitigations-large_en)). Québec's Law 25 requires a privacy impact assessment before deploying systems involving personal information, naming AI systems as an example (s.3.3), and another assessment plus a written agreement before personal information leaves Québec (s.17) ([McCarthy Tétrault](https://www.mccarthy.ca/en/insights/blogs/techlex/quebec-privacy-regulators-guide-law-25-compliant-privacy-impact-assessments)). The federal privacy commissioner's draft third-party guidance, open for comment until 4 December 2026, asks organizations for sub-processor lists, data-flow maps, cross-border assessments, retention including backups, audit rights, and whether consent is needed if a provider uses personal information to train an algorithm ([OPC](https://www.priv.gc.ca/en/privacy-topics/privacy-for-businesses/appropriate-handling-of-personal-information/gd_third-party_202609/)); customers will put exactly these questions to web-agent. The EU AI Act's Digital Omnibus moved Annex III high-risk obligations to **2 December 2027** ([Orrick](https://www.orrick.com/en/Insights/2026/07/EU-AI-Act-Update-Digital-Omnibus-Finalizes-8-Compliance-Changes)), and a dataset connector is unlikely to be an AI system on its own, a conclusion that still needs legal review. SOC 2 has no AI-specific criteria ([arXiv 2604.04749](https://arxiv.org/pdf/2604.04749)), so auditors will sample rule changes and decision logs under existing access-control and change-management criteria. Privacy by default under GDPR Article 25 ([EUR-Lex](https://eur-lex.europa.eu/eli/reg/2016/679/oj)) argues for defaults of no external audience, company scoping that cannot be switched off for customer data, conversation bodies and billing fields excluded, and Write and Manage off. The draft's blank server does the opposite by creating a rule for all four audiences. Enabling an external audience should require confirmation from a data-owner role covering lawful basis and the DPIA, ideally enrolling individual companies ("approve Partner X") rather than whole audiences.

## Version servers like releases and keep five kill switches within reach

### Separate the person who builds a server from the person who publishes it

Every major host platform restricts org-wide publishing to an admin or owner tier. On Claude Team only Owners and Primary Owners can add custom connectors, with Enterprise extending that to a custom role ([Claude Help](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)); on ChatGPT only admins and owners publish MCP apps from a Drafts area after reviewing "safety warnings (especially for write actions)", and role-based access separates who may create connections from who may publish, details that rest on search-snippet text because the help page could not be fetched ([OpenAI Help](https://help.openai.com/en/articles/12584461-creating-custom-mcp-apps-in-chatgpt)). No vendor or spec documents true two-person approval for publishing, so requiring it puts web-agent beyond market practice; standard change management still justifies it for servers open to any external audience, servers with any non-read-only tool, and changes that widen a published server's scope, while internal-only, read-only servers can keep single-approver publishing. Cloudflare illustrates the pattern to avoid, in which "the account that completes upstream OAuth becomes the server's admin credential" ([Cloudflare MCP portals](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/)); web-agent's tools should run under a service identity the publishing workflow controls, never the creator's personal token.

The tool catalog is effectively a **private MCP registry**, and each entry should carry an owner, a risk tier derived from its annotations and the data classes it touches, a review date and pinned provenance, with destructive or open-world tools barred from external-audience servers unless an extra approval is recorded. Thoughtworks placed "naive API-to-MCP conversion" on Hold because wrapping internal APIs leaves no reliable way to stop an agent misusing them ([Thoughtworks Radar](https://www.thoughtworks.cn/radar/techniques/naive-api-to-mcp-conversion)), which validates web-agent's explicit selection from a curated catalog. The official MCP Registry remains in preview, verifies namespaces through GitHub, DNS or HTTP challenges, treats each published version as immutable, and "does not support private servers" ([MCP Registry](https://modelcontextprotocol.io/registry/about); [Versioning](https://modelcontextprotocol.io/registry/versioning)), so public `webagent.dev` servers could be listed under a DNS-verified namespace while partner-specific servers stay in web-agent's own catalog. Server Cards (SEP-2127), which advertise server metadata before connection, were accepted in August 2026 with their `.well-known` path still contested, so the ADR should not commit to one yet ([SEP-2127](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2127)).

### Version the manifest, not the URL, and refuse to serve unapproved definitions

The protocol still neither pins nor signs tool definitions. SEP-3452 proposed mandatory description pinning on 24 October 2026 and was closed two days later on process grounds with no technical ruling ([SEP-3452](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/3452)). Platforms diverge on upstream change: OpenAI lands refreshed actions deselected by default (per its help-center snippets), Anthropic makes admins remove and re-add a connector to edit it, and Cloudflare auto-enables new upstream tools unless allowlist mode is on ([Cloudflare MCP portals](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/)). Web-agent should therefore treat each publish as an **immutable manifest** of tool IDs, descriptions, schemas, annotations, datasets, audiences and rules, hashed with a canonical serialization such as JCS as SEP-3452 commenters suggested, and the serving layer should refuse to serve any definition that does not match the approved hash. That is the server-side mirror of pinning and the defense against web-agent's own silent drift. The canonical URL stays stable, with an optional `/mcp/<slug>/v<N>` for clients that want to pin, in line with the registry's advice to align remote URLs with versions.

Changes should be classified by risk. Narrowing changes (removing a tool, tightening scope, fixing a typo) can publish automatically with notice, while scope growth (a new tool, a wider dataset, an annotation moving toward write or destructive, a new audience, a material description change) goes back through approval and arrives disabled for connected clients until re-approved, as OpenAI does. The spec supplies the mechanics: `toolsListChanged` notifications to clients subscribed through `subscriptions/listen`, `ttlMs` and `cacheScope` on list results, deterministic tool ordering, and `serverInfo` in each result's `_meta` ([changelog](https://modelcontextprotocol.io/specification/latest/changelog)). New versions should reach the Internal audience before external ones, which is standard progressive delivery rather than MCP-specific guidance. Two caveats remain: a definition hash cannot detect a change in the code behind a tool, so catalog implementations also need code review and pinned versions, and how Claude and ChatGPT react to `toolsListChanged` from a remote connector is undocumented.

### Observability needs OpenTelemetry for operations and an append-only log for audit

OpenTelemetry's MCP conventions, at Development stability and now housed in the `semantic-conventions-genai` repository, name spans `{mcp.method.name} {target}`, standardize attributes such as `gen_ai.tool.name`, `jsonrpc.request.id` and `error.type` and the metric `mcp.server.operation.duration`, and make tool-call arguments and results **opt-in only** because each "may contain sensitive information" ([OTel MCP semconv](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/mcp.md)). The conventions still include `mcp.session.id` even though 2026-07-28 removed protocol sessions, so dashboards should not depend on it; the spec itself deprecates its Logging feature in favor of OpenTelemetry and carries trace context in `_meta` ([changelog](https://modelcontextprotocol.io/specification/latest/changelog)). Audit needs a separate append-only log whose records capture the request ID, slug and manifest version, the principal (stable ID, audience, unit, department, company and the source of each attribute), OAuth client and scopes, tool and datasets, the decision with its determining rules and policy version, record IDs returned (or a hash and count), bytes and masked fields, before-and-after references for writes, and the confirmation outcome. Arguments should be stored as a redacted template plus a keyed HMAC of sensitive values, so investigators can match "who searched for X" without the log storing X. Tamper evidence can come from write-once storage or hash chaining, with streaming to customers' SIEMs and a configurable retention default of around one year plus legal hold, balancing GDPR's storage limitation against audit needs. The spec asks servers to log scope-elevation events with correlation IDs ([Security Best Practices](https://modelcontextprotocol.io/specification/latest/basic/security_best_practices)), and Atlassian already writes MCP tool invocations and first-time app installs to the org audit log ([Atlassian](https://www.atlassian.com/blog/announcements/atlassian-rovo-mcp-ga)), which sets the bar customer admins will expect.

### Budgets, kill switches and a retirement path that never frees a slug

The draft documents `monthlyBudget` as "Calls stop for everyone when the month's tool spend reaches it", which turns one runaway agent or stolen token into an outage for every user, the pattern CoSAI calls "denial of wallet" ([CoSAI](https://www.coalitionforsecureai.org/wp-content/uploads/2026/03/model-context-protocol-security-1.pdf)). Budgets should be split per person and per company, with a soft warning near 80%, a hard stop and an audited admin override, and throttled calls should return a structured error the client can display. Useful anomaly signals include the destructive-call rate per principal against baseline, bytes returned per call and per day, bursts from new principals, error spikes after a publish (a rollback trigger), calls from unexpected audiences or tenants, and calls to deprecated tools.

| Kill switch | What it stops | Mechanism |
|---|---|---|
| Principal | One person or one stolen token | Revoke the refresh token and deny at the policy decision point; customer IdP deprovisioning also works where Claude managed authorization is used |
| Audience or company | One partner, reseller or client org | Revoke the relationship grant or suspend the company's enrollment |
| Tool | One catalog tool across every server | Disable it in the catalog so manifests that include it fail closed for that tool |
| Server version | A bad publish | Roll back to the previous immutable manifest |
| Server | The whole slug | Unpublish, return an explicit error at the URL and drop it from discovery |

Claude's managed authorization already makes the customer's IdP a revocation point, since deprovisioning a user removes their connector access ([Claude Help](https://support.claude.com/en/articles/15537633-authorize-mcp-connectors-for-your-entire-organization)). Retirement should run from deprecation, to an announced date, to refusing new connections while existing ones still work, to an explicit "server retired" error at the URL, with the slug reserved forever. The spec's own minimum twelve-month deprecation window is a reasonable ceiling for external audiences, and internal servers can move faster.

### Customer admins expect Atlassian-style controls

Atlassian, the clearest documented example of a SaaS vendor publishing its own MCP server, lets customer admins remove trusted domains to prevent AI tools from reaching their apps, toggle API-token authentication, enforce IP allowlists and review MCP events in the org audit log ([Atlassian Support](https://support.atlassian.com/security-and-access-policies/docs/control-atlassian-rovo-mcp-server-settings/)). Customers' own host platforms filter servers through Claude Code's `allowedMcpServers` and GitHub's "Registry only" policy ([Claude Code Docs](https://code.claude.com/docs/en/managed-mcp); [GitHub Docs](https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-mcp-usage/configure-mcp-server-access)), both of which depend on stable URLs and tool names. Client, partner and reseller admins therefore need their own console, separate from web-agent's publisher admin, where they can see which servers their people connected from which AI clients and when, disconnect one person or the whole organization, restrict which AI clients may connect, watch usage against limits, export audit logs, and receive notice of new versions, scope growth and deprecations. Host platforms place vetting on the customer, with Anthropic warning that custom connectors reach "arbitrary services that have not been verified by Anthropic" ([Claude Help](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)), so security questionnaires will follow; a per-server trust page listing manifest version, tools with annotations, data classes, changelog and status would answer most of them. This research found no primary sources on contract terms for exposing data to resellers or partners through MCP, so the terms need legal review, covering at least that the customer's chosen AI client sits outside web-agent's processing chain, reseller onward transfer, and the deprecation notice period web-agent commits to.

## Conclusion

The central shift is that MCP security in late 2026 is less a protocol problem than a policy-product problem. The 2026-07-28 spec has closed most transport and OAuth gaps through stateless requests, audience-bound tokens, CIMD and issuer validation, and what remains (prompt injection through returned data, permission drift, silent change and cross-tenant mistakes) lives in exactly the layer web-agent is building: the rules editor, the catalog and the publishing workflow. **The admin UX is the security boundary.** The trifecta check, the resolver semantics, the change classifier and the kill switches are security controls that happen to have a user interface, and they deserve the testing and audit that implies. The same discipline is also a commercial advantage, because host platforms give customers allow, ask and block toggles that only work when annotations are honest and manifests are stable, so a server that guarantees both becomes the easiest one for a customer admin to approve.

The most consequential open design choice is whether a single slug should serve Internal and external audiences together. The spec permits it, since `tools/list` may vary by authorization, but separate slugs would give each audience its own token audience, kill switch, trifecta posture and consent screen, at the cost of more servers to manage. Three verifications should precede the ADR: elicitation support in Claude and ChatGPT (if absent, every confirmation routes through the web-agent app, reshaping the UX of each destructive tool), the protocol versions those clients send (which decides how long the 2025 fallback lives), and CIMD and ID-JAG support in the chosen authorization-server vendor. Four-eyes publishing and per-company enrollment would exceed what any host platform requires today, a deliberate choice justified by the external-audience exposure rather than by precedent.
