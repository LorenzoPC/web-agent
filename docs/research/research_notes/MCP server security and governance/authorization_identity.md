# Authorization, authentication and identity for remote MCP servers (state as of October 2026)

Scope: what a remote MCP server at `https://webagent.dev/mcp/<slug>` must and should do for authorization and identity under the current MCP spec, plus what Claude and ChatGPT require in practice. Research date: 2026-10-26. Version labels are used throughout: **2025-03-26**, **2025-06-18**, **2025-11-25**, **2026-07-28** (current).

## Q1. Latest MCP spec version and what its authorization section requires; changes across versions

### Takeaway
The current MCP specification is **2026-07-28** (final, published 28 July 2026 after a May release candidate). Its authorization model treats the MCP server purely as an OAuth 2.1 **resource server** that MUST publish RFC 9728 Protected Resource Metadata. Clients MUST send RFC 8707 `resource`, use PKCE S256 and (new in 2026-07-28) validate RFC 9207 `iss`. Servers MUST validate audience and MUST NOT accept or pass through foreign tokens. Scopes are challenged incrementally through `WWW-Authenticate`, and DCR is now formally deprecated in favor of Client ID Metadata Documents (CIMD).

### Cited Findings

**Current version and status**
- `/specification/latest/basic/authorization` resolves to 2026-07-28 content, and all internal links point to `/specification/2026-07-28/...` — [MCP Authorization (latest)](https://modelcontextprotocol.io/specification/latest/basic/authorization)
- The 2026-07-28 changelog lists changes "since the previous revision, 2025-11-25" — [MCP 2026-07-28 Key Changes](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- Search results say the final 2026-07-28 spec was published 28 July 2026 after a release candidate in May. This comes from search snippets; the blog post itself was not fetched — [MCP blog: The 2026-07-28 Specification](https://blog.modelcontextprotocol.io/posts/2026-07-28/); [MCP blog: Release Candidate](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/)
- Authorization is OPTIONAL. When supported, HTTP-based transports SHOULD conform to it, and STDIO SHOULD NOT (it takes credentials from the environment instead) — [MCP Authorization (2026-07-28)](https://modelcontextprotocol.io/specification/latest/basic/authorization)
- Standards it builds on (2026-07-28): OAuth 2.1 draft-ietf-oauth-v2-1-13, RFC 6750, RFC 8414, RFC 7591, RFC 8707, RFC 9728, RFC 9207, draft-ietf-oauth-client-id-metadata-document-00, OIDC Discovery 1.0 and OIDC Dynamic Client Registration 1.0 — [MCP Authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization)

**Roles and core MUSTs (2026-07-28)**
- "A protected MCP server acts as an OAuth 2.1 resource server". The authorization server "may be hosted with the resource server or a separate entity" — [MCP Authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization)
- Authorization servers MUST implement OAuth 2.1 for both confidential and public clients. Authorization servers and clients SHOULD support CIMD and MAY support DCR, which "is deprecated and retained for backwards compatibility" — [MCP Authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization)
- "MCP servers MUST implement OAuth 2.0 Protected Resource Metadata (RFC9728). MCP clients MUST use [it] for authorization server discovery." Authorization servers MUST provide RFC 8414 metadata or OIDC Discovery 1.0, and clients MUST support both — [MCP Authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization)

**Protected Resource Metadata (RFC 9728) discovery**
- The PRM document MUST include `authorization_servers` with at least one authorization server. When several are listed, the client chooses one per RFC 9728 §7.6 and MUST keep separate registration state for each — [Authorization Server Discovery (2026-07-28)](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery)
- Servers MUST implement one of two discovery mechanisms: (1) `resource_metadata` in `WWW-Authenticate` on a 401, or (2) a well-known URI. The well-known URI can sit at the MCP endpoint's path (for example `https://example.com/public/mcp` maps to `https://example.com/.well-known/oauth-protected-resource/public/mcp`) or at the root `/.well-known/oauth-protected-resource`. Clients MUST support both and probe in that order — [Authorization Server Discovery](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery)
- In 2025-11-25, SEP-985 aligned PRM discovery with RFC 9728, "making `WWW-Authenticate` header optional with fallback to `.well-known` endpoint" — [MCP 2025-11-25 changelog](https://modelcontextprotocol.io/specification/2025-11-25/changelog)

**Authorization server metadata / OIDC discovery**
- For issuers with a path (for example `https://auth.example.com/tenant1`), clients MUST try in order: `/.well-known/oauth-authorization-server/tenant1`, `/.well-known/openid-configuration/tenant1`, then `/tenant1/.well-known/openid-configuration`. For issuers without a path: `/.well-known/oauth-authorization-server`, then `/.well-known/openid-configuration` — [Authorization Server Discovery](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery)
- The `issuer` in the fetched metadata "MUST be identical to the issuer identifier used to construct the well-known URL. If they differ, the client MUST NOT use the metadata" — [Authorization Server Discovery](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery)
- OIDC Discovery support was added in 2025-11-25 (PR #797) — [MCP 2025-11-25 changelog](https://modelcontextprotocol.io/specification/2025-11-25/changelog)

**PKCE**
- Clients MUST implement PKCE, MUST use `S256` when technically capable, and MUST check PKCE support before proceeding. If `code_challenge_methods_supported` is absent from RFC 8414 or OIDC metadata, clients "MUST refuse to proceed". "Authorization servers providing OpenID Connect Discovery 1.0 MUST include `code_challenge_methods_supported`" — [Security Considerations (2026-07-28)](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)

**Resource indicators (RFC 8707) and canonical URI**
- Clients MUST send `resource` in both authorization and token requests. It MUST identify the MCP server, MUST be the server's canonical URI, and MUST be sent "regardless of whether authorization servers support it" — [MCP Authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization)
- Valid canonical URIs include `https://mcp.example.com/server/mcp` "(when path component is necessary to identify individual MCP server)". Fragments are invalid. Implementations SHOULD use the form without a trailing slash — [MCP Authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization)
- RFC 8707 was made mandatory for clients in 2025-06-18 (PR #734) "to prevent malicious servers from obtaining access tokens" — [MCP 2025-06-18 changelog](https://modelcontextprotocol.io/specification/2025-06-18/changelog)

**Token audience validation and the passthrough ban**
- "MCP servers MUST validate that access tokens were issued specifically for them as the intended audience" (RFC 8707 §2). Invalid or expired tokens MUST get a 401. "MCP servers MUST only accept tokens that are valid for use with their own resources. MCP servers MUST NOT accept or transit any other tokens." Clients "MUST NOT send tokens to the MCP server other than ones issued by the MCP server's authorization server" — [MCP Authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization)
- When calling upstream APIs, the MCP server acts as an OAuth client with a separate token and "MUST NOT pass through the token it received from the MCP client" — [Security Considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)
- The best-practices page gives the reasons passthrough is forbidden: it bypasses security controls, breaks the audit trail (the server "will be unable to identify or distinguish between MCP Clients"), creates trust-boundary issues and adds future-compatibility risk. Mitigation: "MCP servers MUST NOT accept any tokens that were not explicitly issued for the MCP server" — [Security Best Practices (2026-07-28)](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)
- Tokens MUST travel in the `Authorization: Bearer` header on every HTTP request and MUST NOT appear in the query string — [MCP Authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization)

**WWW-Authenticate, scope selection, step-up (incremental consent)**
- Servers SHOULD include `scope` in the 401 `WWW-Authenticate` challenge. Clients MUST treat the challenged scopes as authoritative for the current operation. Initial scope priority for clients: the challenge's `scope` first, otherwise all of PRM `scopes_supported`. `scopes_supported` "is intended to represent the minimal set of scopes necessary for basic functionality" — [MCP Authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization)
- At runtime, an insufficient scope SHOULD get `403` with `WWW-Authenticate: Bearer error="insufficient_scope", scope="...", resource_metadata="..."`. Servers SHOULD put every scope the current operation needs into a single challenge rather than one at a time. Clients SHOULD re-authorize with the union of previously requested and newly challenged scopes, and SHOULD cap retries. "Servers MUST account for scope hierarchies" — [MCP Authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization)
- Incremental scope consent through `WWW-Authenticate` arrived in 2025-11-25 (SEP-835) — [MCP 2025-11-25 changelog](https://modelcontextprotocol.io/specification/2025-11-25/changelog)
- Scope-minimization guidance: start with a minimal scope set (for example `mcp:tools-basic`) and elevate through targeted challenges. Listed as common mistakes: "Publishing all possible scopes in `scopes_supported`", wildcard or omnibus scopes, and "Treating claimed scopes in token as sufficient without server-side authorization logic" — [Security Best Practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)
- Status codes: 401 when authorization is required or the token is invalid, 403 for invalid scopes or insufficient permissions, 400 for a malformed request — [MCP Authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization)

**Issuer validation (new in 2026-07-28)**
- Authorization servers SHOULD include `iss` in authorization responses (RFC 9207) and MUST then advertise `authorization_response_iss_parameter_supported: true`. Clients MUST compare a present `iss` against the recorded issuer and MUST reject a response that lacks `iss` when the metadata advertises it. A future revision "is expected to upgrade authorization server inclusion of `iss` from SHOULD to MUST" — [MCP Authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization); SEP-2468 in [2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)

**Refresh tokens (2026-07-28 text)**
- Clients that want refresh tokens MUST keep them confidential, SHOULD include `refresh_token` in `grant_types`, MAY add `offline_access` when the authorization server lists it, and MUST NOT assume one will be issued. MCP servers "SHOULD NOT include `offline_access` in `WWW-Authenticate` scope or Protected Resource Metadata `scopes_supported`" — [MCP Authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization)

**Security considerations (2026-07-28)**
- Authorization servers SHOULD issue short-lived access tokens. "For public clients, authorization servers MUST rotate refresh tokens." All authorization server endpoints MUST use HTTPS, and redirect URIs MUST be localhost or HTTPS. Authorization servers MUST do exact redirect-URI matching. For CIMD, authorization servers SHOULD consider SSRF, SHOULD warn on localhost-only redirect URIs, and MUST clearly show the redirect URI hostname. "MCP proxy servers using static client IDs MUST obtain user consent for each dynamically registered client" — [Security Considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)
- Statelessness (2026-07-28 removes `Mcp-Session-Id`): servers "MUST NOT treat possession of a state handle as authentication" and SHOULD bind handles server-side to the user ID taken from the verified token, for example `<user_id>:<handle>` — [Security Best Practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices); SEP-2567/2575 in [2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)

**Version-by-version deltas**
- **2025-03-26:** the MCP server was effectively the authorization server. Clients MUST use RFC 8414 metadata at an "authorization base URL" formed by discarding the MCP URL path, falling back to default `/authorize`, `/token` and `/register` endpoints. DCR was SHOULD, PKCE was REQUIRED, and a "Third-Party Authorization Flow" had the MCP server act as both OAuth client to a third-party AS and AS to the MCP client, issuing "its own access token bound to the third-party session" — [MCP Authorization 2025-03-26](https://modelcontextprotocol.io/specification/2025-03-26/basic/authorization)
- **2025-06-18:** MCP servers reclassified as OAuth resource servers with PRM discovery (PR #338). RFC 8707 required for clients (PR #734). New security best-practices page (token passthrough, confused deputy) — [MCP 2025-06-18 changelog](https://modelcontextprotocol.io/specification/2025-06-18/changelog)
- **2025-11-25:** OIDC Discovery (PR #797), incremental scope consent through `WWW-Authenticate` (SEP-835), CIMD as a recommended registration mechanism (SEP-991 / PR #1296), `WWW-Authenticate` made optional with well-known fallback (SEP-985), and URL-mode elicitation (SEP-1036) — [MCP 2025-11-25 changelog](https://modelcontextprotocol.io/specification/2025-11-25/changelog)
- **2026-07-28:** RFC 9207 `iss` validation (SEP-2468), `application_type` required in DCR (SEP-837), client credentials bound to the issuing AS (SEP-2352), DCR deprecated (PR #2858), a feature-lifecycle policy with a minimum 12-month deprecation window (SEP-2596), and a stateless protocol with no sessions and no `initialize` (SEP-2567/2575) — [MCP 2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- Authorization extensions live in the `ext-auth` repo. Both "Enterprise-Managed Authorization" and "OAuth Client Credentials" are listed as **Stable** with 2026-07-28 spec files — [modelcontextprotocol/ext-auth](https://github.com/modelcontextprotocol/ext-auth)

### Inferences
- webagent.dev's MCP endpoints must return a 401 carrying `resource_metadata` and a minimal `scope`, serve per-slug PRM (for example `https://webagent.dev/.well-known/oauth-protected-resource/mcp/<slug>`), and validate `aud`/`resource` against the exact slug URL on every request.
- Because the spec calls `scopes_supported` "minimal" and favors step-up, Read/Write/Manage could map to coarse OAuth scopes (for example `datasets:read`, `datasets:write`). The per-dataset, per-audience, per-BU/department matrix should still be enforced server-side at call time, since the spec warns against treating token scopes as sufficient.
- Statelessness in 2026-07-28 means the identity for every tool call comes from the bearer token on that call, with no session to lean on. That simplifies per-request policy evaluation.

### Gaps
- I did not read any post-2026-07-28 "draft" spec changes on GitHub, so changes pending for the next revision are unverified.
- The 2026-07-28 release date comes from search-result snippets; the release blog post was not fetched.
- I did not confirm whether the `offline_access` / refresh-token section is new in 2026-07-28 or carried over from 2025-11-25. The changelog does not list it.

## Q2. Client registration: DCR vs CIMD vs pre-registration

### Takeaway
2026-07-28 makes **CIMD the preferred mechanism** (SHOULD) for clients with no prior relationship, keeps **pre-registration** as first priority when available, and **deprecates DCR** (MAY, backwards-compatibility only). Claude and ChatGPT both support CIMD and DCR, and Claude explicitly recommends CIMD over DCR for busy servers. The security trade-offs are open-DCR client sprawl and consent-skipping on one side, and SSRF, localhost impersonation and phishing via client metadata on the other.

### Cited Findings
- Client priority order: (1) pre-registered client info, (2) CIMD if the AS advertises `client_id_metadata_document_supported`, (3) DCR if `registration_endpoint` exists, (4) prompt the user to enter client info — [Client Registration (2026-07-28)](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)
- CIMD requirements: the `client_id` is an HTTPS URL with a path component; the document MUST contain `client_id`, `client_name` and `redirect_uris`, and its `client_id` MUST match the URL exactly. Authorization servers SHOULD fetch and cache the document (respecting HTTP cache headers), MUST validate redirect URIs against it, and MUST validate its structure. Clients MAY use `private_key_jwt` — [Client Registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)
- CIMD portability: CIMD client IDs "are portable across authorization servers … No re-registration is needed when the authorization server changes", unlike pre-registered or DCR credentials, which clients MUST key by `issuer` and MUST NOT reuse with another AS (SEP-2352) — [Client Registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)
- DCR deprecation: "Dynamic Client Registration is deprecated. New implementations should use Client ID Metadata Documents instead." Clients doing DCR MUST send `application_type` (`native` for desktop/CLI/localhost, `web` for remote browser apps), because OIDC servers default to `web` and reject loopback redirect URIs — [Client Registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)
- Pre-registration: "MCP clients SHOULD support an option for static client credentials", either hard-coded or entered by the user in a UI — [Client Registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)
- DCR/consent abuse: the confused-deputy attack needs a static upstream client ID, DCR, an upstream consent cookie and no per-client consent at the proxy. Proxies MUST then keep per-user registries of approved `client_id`s, show a consent UI with client name, scopes and `redirect_uri`, use `__Host-` signed cookies bound to `client_id`, and match redirect URIs exactly — [Security Best Practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)
- CIMD risks: the AS fetches attacker-supplied URLs (SSRF), so block private ranges and use egress proxies. A metadata document "cannot prove which local process is listening on a localhost redirect URI", so an attacker can present a legitimate client's metadata URL with their own localhost port. Authorization servers MAY apply domain trust policies (allowlists, reputation, domain age) and should "Display the CIMD and other associated client hostnames prominently to prevent phishing" — [Security Best Practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices); [Security Considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)
- Cloudflare warns that enabling DCR without an approval step lets any client self-register and request permissions (Descope section) — [Cloudflare: MCP Authorization](https://developers.cloudflare.com/agents/model-context-protocol/authorization/)
- Claude: "DCR causes Claude to register a new client on every fresh connection, which can result in very large numbers of registered clients on your authorization server. CIMD and Anthropic-held credentials avoid the registration call entirely" — [Claude: Authentication for connectors](https://claude.com/docs/connectors/building/authentication.md)
- ChatGPT lists CIMD as "preferred", DCR (registers once per MCP server connection) and predefined OAuth clients — [OpenAI Apps SDK: Auth](https://developers.openai.com/apps-sdk/build/auth)

### Inferences
- For webagent.dev's authorization server, support **CIMD with a domain trust policy** (allowlist `claude.ai` / Anthropic's CIMD host, ChatGPT's CIMD host and VS Code, plus an admin-approved list for other clients) and **pre-registration** for enterprise/EMA cases. Offer DCR only as a gated fallback, or omit it, because it is deprecated and creates client sprawl.
- An allowlist of client domains doubles as a governance control: admins can restrict which MCP clients may connect to a given `/mcp/<slug>`.

### Gaps
- I did not check whether the CIMD IETF draft has moved past -00. The MCP spec still cites -00.
- Exact CIMD URLs for ChatGPT and other clients were not retrieved. Claude Code's is `https://claude.ai/oauth/claude-code-client-metadata` per the Claude docs; the CIMD URL for claude.ai web was not stated.

## Q3. Enterprise-managed authorization (ID-JAG / Cross App Access, token exchange, SSO), multi-tenant identity mapping, directory attributes

### Takeaway
The MCP **Enterprise-Managed Authorization (EMA)** extension is **Stable** as of 2026. It lets a client exchange the user's enterprise SSO assertion for an **ID-JAG** at the IdP (RFC 8693 token exchange), then present it at the MCP server's AS with the **RFC 7523 JWT-bearer grant**, with no consent screen. Okta (Cross App Access) is the first supported IdP; Claude (Team/Enterprise) and VS Code (preview) support it; ChatGPT's auth doc says it does not support JWT-bearer grants. For multi-tenant identity, key users on the (issuer, subject) pair, or Entra `tid`+`oid`, never on email or UPN. Department and business-unit data do not appear in default IdP tokens and need claims customization or SCIM provisioning.

### Cited Findings

**EMA / ID-JAG mechanics**
- EMA lets an MCP client "obtain access tokens for MCP Servers using an identity assertion from the enterprise's single sign-on". Flow: SSO (OIDC or SAML), then RFC 8693 token exchange at the IdP for an ID-JAG, then RFC 7523 `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer` at the MCP AS, then an access token. In the token exchange, `audience` "MUST be the issuer identifier of the Resource Authorization Server", and the issued access token "MUST be audience-restricted to the MCP Server identified by the `resource` claim". Discovery is through `urn:ietf:params:oauth:grant-profile:id-jag` in `authorization_grant_profiles_supported` — [ext-auth: Enterprise-Managed Authorization 2026-07-28](https://raw.githubusercontent.com/modelcontextprotocol/ext-auth/main/specification/stable/enterprise-managed-authorization/2026-07-28/enterprise-managed-authorization.mdx)
- EMA security notes: IdP policy "typically allows sign-in only for pre-registered clients". IdP visibility "does not extend to the actual MCP traffic between the MCP Client and Server". The IdP can control which users use which clients against which servers, and possibly scopes — [ext-auth EMA spec](https://raw.githubusercontent.com/modelcontextprotocol/ext-auth/main/specification/stable/enterprise-managed-authorization/2026-07-28/enterprise-managed-authorization.mdx)
- The IETF draft is draft-ietf-oauth-identity-assertion-authz-grant-04 (21 May 2026, OAuth WG; authors Parecki/Okta, McGuinness, Campbell/Ping), informally "Cross-App Access (XAA)". `requested_token_type=urn:ietf:params:oauth:token-type:id-jag`. Required claims: `iss`, `sub`, `aud`, `client_id`, `jti`, `exp`, `iat`, with `typ` `oauth-id-jag+jwt`. Optional claims include `resource`, `scope`, `tenant`, `aud_tenant`, `aud_sub`, `email`, `acr`, `amr` and `auth_time` — [IETF Datatracker: ID-JAG](https://datatracker.ietf.org/doc/draft-ietf-oauth-identity-assertion-authz-grant/)
- The MCP blog (18 June 2026) says EMA is stable and "Okta is the first supported identity provider". Anthropic implemented it "in its shared MCP layer for Claude" across Claude, Claude Code and Cowork. VS Code support is in preview. Servers include Asana, Atlassian, Canva, Figma, Granola, Linear and Supabase. ChatGPT is not mentioned — [MCP blog: Enterprise-Managed Auth](https://blog.modelcontextprotocol.io/posts/enterprise-managed-auth/)
- Auth0 marks "Cross App Access (XAA) for the Resource App" as Early Access (from a search snippet; page not fetched) — [Auth0: Cross App Access](https://auth0.com/docs/ai-agents-mcp/cross-app-access.md)

**Claude's EMA requirements for the server's AS**
- EMA is "available on Claude Team and Enterprise plans". "Dynamic Client Registration (DCR) isn't supported with Enterprise Managed Auth", so the AS must recognize Claude through Anthropic-held credentials or CIMD. The AS must accept the JWT-bearer grant **and list it in `grant_types_supported`** ("Claude reads this metadata to discover whether your server supports Enterprise Managed Auth"). It must keep "an explicit allowlist of trusted issuer URLs per tenant" and reject an unlisted `iss` with `invalid_grant`. `resource` may be absent when the IdP can't forward it. Claude uses the IdP refresh token to mint fresh ID-JAGs silently. The product should offer customer admins an EMA toggle plus an "identity provider's issuer URL" field — [Claude: Enterprise Managed Auth](https://claude.com/docs/connectors/building/enterprise-managed-auth.md)
- Testing: Okta's playground at https://xaa.dev and Okta's Claude EMA "beta participation guide" — [Claude: Enterprise Managed Auth](https://claude.com/docs/connectors/building/enterprise-managed-auth.md)
- **Discrepancy:** the ext-auth spec says clients detect support through `authorization_grant_profiles_supported` containing the id-jag profile, while Claude's doc says it looks for jwt-bearer in `grant_types_supported` — [ext-auth EMA spec](https://raw.githubusercontent.com/modelcontextprotocol/ext-auth/main/specification/stable/enterprise-managed-authorization/2026-07-28/enterprise-managed-authorization.mdx) vs [Claude EMA doc](https://claude.com/docs/connectors/building/enterprise-managed-auth.md)

**Identity mapping in a multi-tenant SaaS**
- Claude: "Scope what each user can reach with your service's own per-user permissions rather than with a per-tenant OAuth app" — [Claude: Authentication for connectors](https://claude.com/docs/connectors/building/authentication.md)
- Microsoft Entra: `email` "isn't guaranteed to be correct, and is mutable over time - never use it for authorization". UPN is "Not a durable identifier … use the user object ID (`oid`) as a database key". The `acct` claim distinguishes members (0) from guests (1). `xms_edov` indicates a verified email-domain owner — [Entra optional claims reference](https://learn.microsoft.com/en-us/entra/identity-platform/optional-claims-reference)
- ChatGPT workspace domain restrictions require `openid` and `email` plus a UserInfo endpoint returning `email` and `email_verified: true` — [OpenAI Apps SDK: Auth](https://developers.openai.com/apps-sdk/build/auth)

**Directory attributes (business unit, department)**
- Entra's default optional-claims set does **not** include `department` or `jobTitle`. "You can use custom data in extension attributes and directory extensions to add optional claims." `groups` needs `GroupMembershipClaims` in the manifest. Optional claims are configured per token type and per application — [Entra optional claims reference](https://learn.microsoft.com/en-us/entra/identity-platform/optional-claims-reference)
- Community guidance shows emitting `department` through claims-mapping policies or by mapping the `user.department` source attribute. This is not authoritative, and the Microsoft Q&A answer is from 2021 — [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/308500/how-to-add-specific-json-optionalclaims); [Zscaler Entra guide](https://help.zscaler.com/unified/configuring-microsoft-entra-id-external-idp)
- SCIM 2.0's Enterprise User extension (`urn:ietf:params:scim:schemas:extension:enterprise:2.0:User`) defines `employeeNumber`, `costCenter`, `organization`, `division`, `department` and `manager`. This is cited from the RFC, which was not re-fetched in this session — [RFC 7643 §4.3](https://datatracker.ietf.org/doc/html/rfc7643#section-4.3)

### Inferences
- For **Internal staff**, EMA through webagent's own IdP (for example Okta XAA) can give zero-consent access in Claude Team/Enterprise. For **Clients, Partners and Resellers**, each external org would have to register its own IdP issuer with webagent, which is exactly the per-tenant trusted-issuer allowlist Claude describes. That suits large partners; smaller ones will use the interactive OAuth flow.
- Advertise **both** `grant_types_supported` (jwt-bearer) and `authorization_grant_profiles_supported` (id-jag) to satisfy Claude's detection and the spec's.
- Use `(iss, sub)` of the upstream IdP, or Entra `tid`+`oid`, as the external identity key, linked to a webagent account and tenant (the audience org). Use a verified email domain only as a hint for which tenant to route to, never as the authorization key.
- BU and department should come from a **webagent-side directory record** populated by SCIM provisioning (preferred for enterprise tenants), by per-tenant claim mapping at federation time, or by admin entry. Read them at request time rather than trusting token claims, because claims are often missing, stale until the next login, and configured differently per IdP.

- Okta custom-claim and Google Workspace department-attribute specifics were not researched. Google ID tokens are believed not to carry department; that needs the Admin SDK Directory API (unverified).
- I did not confirm whether ChatGPT added EMA after the Apps SDK auth page was written.

## Q4. Should the MCP server be its own authorization server or delegate to an external IdP/AS?

### Takeaway
Since 2025-06-18 the spec separates the MCP server (resource server) from the AS, which "may be hosted with the resource server or a separate entity". The 2025-03-26 "MCP server is the AS" model with default endpoints is legacy. Clients and vendors push toward an **established, standards-complete AS** (OpenAI "strongly" recommends one) that supports CIMD, PKCE, RFC 8707, RFC 9207 and, for enterprise, JWT-bearer/ID-JAG. That AS is typically **federated to each customer's IdP** rather than having the MCP server proxy upstream tokens.

### Cited Findings
- 2026-07-28: AS implementation details are "beyond the scope … It may be hosted with the resource server or a separate entity" — [MCP Authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization)
- 2025-03-26 assumed the MCP server also acted as the AS ("The following example assumes the MCP server is also functioning as the authorization server"), with metadata at the domain root and default `/authorize`, `/token` and `/register` — [MCP Authorization 2025-03-26](https://modelcontextprotocol.io/specification/2025-03-26/basic/authorization)
- OpenAI: "We strongly recommend that you use an existing established identity provider", naming Auth0 and Stytch and favoring providers that support CIMD — [OpenAI Apps SDK: Auth](https://developers.openai.com/apps-sdk/build/auth)
- Claude: the AS "can be on a different host from your MCP server". Claude "uses the first entry and doesn't fall back to later entries" in `authorization_servers`. The AS's `/.well-known/` must be reachable from Anthropic's egress range (`160.79.104.0/21`), and "a WAF in front of your identity provider can break the flow" — [Claude: Authentication for connectors](https://claude.com/docs/connectors/building/authentication.md)
- Claude EMA: "If your MCP server relies on a hosted identity platform, there is typically no code to write … some commercial authorization servers and identity platforms don't support it yet" — [Claude: Enterprise Managed Auth](https://claude.com/docs/connectors/building/enterprise-managed-auth.md)
- Cloudflare's reference stack (Workers OAuth Provider library) offers four patterns: Cloudflare Access; third-party OAuth (GitHub/Google); bring-your-own (Stytch, Auth0, WorkOS, Descope); and self-contained. In the third-party and BYO patterns, "the MCP server issues its own token to the MCP client, bound to the upstream provider's token". The page links the 2025-06-18 spec and does not mention CIMD. It suggests either checking permissions inside a tool handler or registering tools conditionally so the model never sees tools the user can't use — [Cloudflare: MCP Authorization](https://developers.cloudflare.com/agents/model-context-protocol/authorization/)
- Vercel `mcp-handler` (Next.js 13+) is **resource-server-only**. `withMcpAuth` verifies bearer tokens and returns RFC 9728-compliant 401/403 challenges, and `protectedResourceHandler` serves PRM. "CIMD support is advertised and implemented by your authorization server." v2.x uses `@modelcontextprotocol/server` ^2.0.0 and exposes `ctx.http?.authInfo` to tools — [vercel/mcp-handler](https://github.com/vercel/mcp-handler)
- The proxy-as-AS pattern (an MCP server fronting a third-party AS with a static client ID) is exactly the confused-deputy scenario, and per-client consent is mandatory — [Security Best Practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)

### Inferences
- Pros of a webagent-operated or hosted multi-tenant AS (for example WorkOS, Auth0, Stytch, Descope, or a self-built one on a library): a single issuer for all `/mcp/<slug>` resources (which matters because Claude only uses the first AS); control over per-slug audiences, the CIMD trust policy, consent UI, per-tenant SSO connections (OIDC/SAML to client, partner and reseller IdPs) and the EMA trusted-issuer list; and tokens that carry webagent's own user and tenant identifiers.
- Cons: you own OAuth security (RFC 9207, rotation, SSRF-safe CIMD fetches) unless it is hosted, and vendor support for CIMD and JWT-bearer/ID-JAG varies, so verify before choosing (Auth0 XAA is Early Access).
- Delegating directly to a **customer's** IdP (for example a client's Entra) as the AS for `/mcp/<slug>` does not fit a multi-audience server. PRM lists one effective AS for Claude, while four audiences come from many IdPs, and Entra would need each MCP URL registered as an Application ID URI on a verified domain (see Q5). Federation upstream of webagent's AS is the workable pattern.
- `mcp-handler` fits the Next.js stack as the resource-server layer. The AS is a separate component.

- I did not verify current CIMD and JWT-bearer support matrices for WorkOS, Stytch, Descope, Auth0 or Clerk.

## Q5. Token lifetimes, refresh, revocation, audiences; is `/mcp/<slug>` a good resource identifier?

### Takeaway
The spec requires short-lived access tokens (SHOULD), refresh-token rotation for public clients (MUST), and audience binding to the exact MCP server URI (MUST). It explicitly allows a path to identify an individual server, so **one canonical URL per server (`https://webagent.dev/mcp/<slug>`) is a spec-conformant and recommended resource identifier**, with PRM served at the path-inserted well-known URL. The MCP spec defines no revocation mechanism; that falls to standard OAuth.

### Cited Findings
- Authorization servers "SHOULD issue short-lived access tokens". For public clients they "MUST rotate refresh tokens" — [Security Considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations)
- Claude registers as a **public client** through DCR or CIMD. It refreshes "proactively up to five minutes before the stored expiry" and reactively on 401, expects `invalid_grant` for dead refresh tokens, requires form-urlencoded `/token`, and allows 10 s for discovery, registration and token endpoints and 30 s for refresh. Claude appends `offline_access` when the AS lists it — [Claude: Authentication for connectors](https://claude.com/docs/connectors/building/authentication.md)
- Under EMA, "A short lifetime, such as one hour, doesn't force users to repeat single sign-on", because Claude re-mints ID-JAGs from the IdP refresh token. "Treat [the IdP refresh token] as long-lived" — [Claude: Enterprise Managed Auth](https://claude.com/docs/connectors/building/enterprise-managed-auth.md)
- ChatGPT: verify signature (JWKS), `iss`, `exp`/`nbf`, `aud`/`resource` and scopes "on every request". Plan for "token revocation, refresh, and scope changes". Keep the registered client valid, because an expired client causes `invalid_client` — [OpenAI Apps SDK: Auth](https://developers.openai.com/apps-sdk/build/auth)
- Canonical URIs may include a path "when path component is necessary to identify individual MCP server". Clients "SHOULD provide the most specific URI that they can" — [MCP Authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization)
- PRM path insertion: `https://example.com/public/mcp` maps to `https://example.com/.well-known/oauth-protected-resource/public/mcp` — [Authorization Server Discovery](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery)
- Claude: PRM `resource` "must equal the URL as the user enters it in Claude, including any path component". The `resource_metadata` URL can be any HTTPS location, which is "the most reliable path on serverless or edge platforms" that can't serve root `/.well-known/*` — [Claude: Authentication for connectors](https://claude.com/docs/connectors/building/authentication.md)
- Entra as AS: the MCP URL must be registered as an Application ID URI or the request fails with `AADSTS9010010`, and only on a tenant-verified domain by default — [Claude: Authentication for connectors](https://claude.com/docs/connectors/building/authentication.md)
- Entra v1 access tokens can emit `aud` in several forms (app ID URI with or without a trailing slash, or client ID). The `use_guid` property normalizes it — [Entra optional claims reference](https://learn.microsoft.com/en-us/entra/identity-platform/optional-claims-reference)
- Scope minimization lists "higher friction on revocation: revoking a max-privilege token disrupts all workflows" as a risk of broad scopes — [Security Best Practices](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices)

### Inferences
- **Per-server audience (`aud = https://webagent.dev/mcp/<slug>`)** gives isolation: a token for one server cannot be replayed against another. A per-tenant audience would collapse that boundary across servers, so per-server audience is the better default. The AS must validate the `resource` value against the registry of published slugs.
- Changing a slug changes the resource identifier, which breaks existing tokens and connector configs. Treat slugs as immutable, or keep redirects plus legacy-audience acceptance.
- Suggested lifetimes: access tokens around 5–60 minutes (Claude's EMA example uses 1 h); rotating refresh tokens with reuse detection; revocation through RFC 7009 plus server-side deny-lists or short lifetimes. Grant changes (an admin revoking a dataset) should take effect immediately because policy is evaluated per request, not baked into tokens.

### Gaps
- The MCP spec does not mention RFC 7009 revocation or RFC 7662 introspection. No MCP-specific revocation guidance was found.
- I did not confirm Entra limits on the number of Application ID URIs per app, which matters only if Entra were the AS.
- No source gives concrete recommended lifetimes beyond Claude's one-hour EMA example.

## Q6. What Claude and ChatGPT require from a remote MCP server today

### Takeaway
Both clients implement the 2025-11-25-era OAuth profile: PRM, RFC 8414 or OIDC discovery, PKCE S256, `resource`, and CIMD preferred with DCR as fallback. **Claude** also supports Anthropic-held or customer-entered static OAuth clients, Enterprise Managed Auth (Team/Enterprise) and a beta static-header mode, with one fixed callback for hosted apps plus loopback for Claude Code. **ChatGPT** supports CIMD, DCR and predefined clients, uses `chatgpt.com` callbacks, presents an mTLS client certificate, and does not support client-credentials or JWT-bearer grants.

### Cited Findings

**Claude**
- One auth stack covers claude.ai, Desktop, mobile, Claude Code and Cowork. Auth types: `oauth_dcr` and `oauth_cimd` (default), `oauth_anthropic_creds` (developer portal), `custom_connection` (contact Anthropic), `static_headers` (beta, org-Owner-entered, "Treat it as the organization's credential, not a person's"), and `none` — [Claude: Authentication for connectors](https://claude.com/docs/connectors/building/authentication.md)
- Claude uses CIMD only if the AS advertises `client_id_metadata_document_supported: true` **and** `none` in `token_endpoint_auth_methods_supported`; otherwise it falls back to DCR — [Claude: Authentication](https://claude.com/docs/connectors/building/authentication.md)
- Callback for hosted apps: exactly `https://claude.ai/api/mcp/auth_callback`. Claude Code uses RFC 8252 loopback (`http://localhost/callback`, `http://127.0.0.1/callback`) with a port-agnostic match and its own CIMD at `https://claude.ai/oauth/claude-code-client-metadata` — [Claude: Authentication](https://claude.com/docs/connectors/building/authentication.md)
- A search snippet says the callback "may move to `https://claude.com/api/mcp/auth_callback`", so allowlisting both is advised. This claim was **not** in the fetched authentication page — [support.claude.com 11503834](https://support.claude.com/en/articles/11503834) (search result only; the full article returned 404)
- Strictness beyond the spec: sign-in starts only on a 401 (a `WWW-Authenticate` on a 200 is ignored), only the first `authorization_servers` entry is used, S256 PKCE is always sent, scopes come from the challenge or else `scopes_supported`, and there is no `client_credentials` grant — [Claude: Authentication](https://claude.com/docs/connectors/building/authentication.md)
- Custom connectors: a customer adding by URL authenticates via Anthropic's CIMD, DCR, or an OAuth client ID (secret optional) the customer registered and enters in the dialog. An org-admin-entered client takes precedence over listing and Anthropic clients for that URL — [Claude: Authentication](https://claude.com/docs/connectors/building/authentication.md)
- Per-customer URLs in the directory can use a URL pattern; CIMD then DCR is the recommended order — [Claude: Authentication](https://claude.com/docs/connectors/building/authentication.md)
- Egress IPs: `160.79.104.0/21` — [Claude: Authentication](https://claude.com/docs/connectors/building/authentication.md)
- EMA is on Team/Enterprise plans; there is no DCR under EMA; the AS needs a jwt-bearer grant and per-tenant issuer allowlist — [Claude: Enterprise Managed Auth](https://claude.com/docs/connectors/building/enterprise-managed-auth.md)

**ChatGPT (Apps SDK / connectors / developer mode)**
- Requires PRM (well-known or `WWW-Authenticate`), RFC 8414 or OIDC metadata with `code_challenge_methods_supported` including S256 ("Servers are unsupported if [it] omits S256"), and `resource` in authorization and token requests, which the AS should copy into `aud` — [OpenAI Apps SDK: Auth](https://developers.openai.com/apps-sdk/build/auth)
- Registration: CIMD preferred (token endpoint auth `none` or `private_key_jwt`), DCR (one registration per connection), or predefined clients — [OpenAI Apps SDK: Auth](https://developers.openai.com/apps-sdk/build/auth)
- Redirects: `https://chatgpt.com/connector_platform_oauth_redirect` for servers meeting the RFC 9207 `iss` requirements, otherwise `https://chatgpt.com/connector/oauth/{callback_id}` (copy the exact value from the management page) — [OpenAI Apps SDK: Auth](https://developers.openai.com/apps-sdk/build/auth)
- Transport identity: ChatGPT presents an OpenAI-managed client certificate (SAN `mtls.prod.connectors.openai.com`; don't pin the leaf). Allowlisting published egress IPs is the alternative — [OpenAI Apps SDK: Auth](https://developers.openai.com/apps-sdk/build/auth)
- Per-tool `securitySchemes` (`noauth`, `oauth2` with scopes). The auth UI is triggered by a tool error carrying `_meta["mcp/www_authenticate"]` (for example `insufficient_scope`). "ChatGPT does not support client credentials, service accounts, or JWT bearer grants." Requests OIDC `openid email profile` by default; honoring `id_token_hint` is optional — [OpenAI Apps SDK: Auth](https://developers.openai.com/apps-sdk/build/auth)
- Admin controls (search snippet only; the help page returned 403): developer mode and custom MCP apps are available on ChatGPT web for Business and Enterprise/Edu. Enterprise/Edu admins can grant developer mode by RBAC, choose who can access each app, choose allowed actions before publishing, and see risk warnings for write-capable apps. Only admins and owners publish — [OpenAI Help: Developer mode and MCP apps](https://help.openai.com/en/articles/12584461-developer-mode-and-mcp-apps-in-chatgpt)

### Inferences
- A webagent AS that satisfies both clients needs to: advertise CIMD plus `none` auth, list `code_challenge_methods_supported: ["S256"]`, emit `iss` with `authorization_response_iss_parameter_supported: true` (which also unlocks ChatGPT's fixed redirect), accept form-urlencoded `/token`, return `invalid_grant` on dead refresh tokens, respond within 10 s, and keep `/.well-known` reachable from Anthropic and OpenAI egress (no WAF blocks).
- Register redirect URIs: `https://claude.ai/api/mcp/auth_callback` (plus `claude.com`, defensively), loopback with any port for Claude Code, `https://chatgpt.com/connector_platform_oauth_redirect`, and the ChatGPT `{callback_id}` form if needed.
- Neither client supports machine-to-machine `client_credentials`, which fits the "work email over OAuth, no API keys" decision. Claude's beta `static_headers` should not be offered, because it erases per-user identity.
- The ChatGPT per-tool `securitySchemes` and Claude "lazy authentication" patterns let public datasets (for example the help center) be served `noauth` while gated tools trigger sign-in. Decide whether any `/mcp/<slug>` server is mixed-mode.
