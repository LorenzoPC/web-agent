# MCP server lifecycle and operational governance (state as of 26 October 2026)

Scope: who creates and publishes servers, how tools get into the catalog, change control, operations (observability, quotas, kill switches, retirement), how platforms and vendors govern MCP today, and what customer-side admins need. OAuth flows, transport hardening, prompt-injection threats and the dataset permission model are out of scope (other researchers cover them).

Source-quality legend used below: **[primary]** = vendor or spec documentation; **[secondary]** = third-party blog or comparison; **[snippet-only]** = text seen only in a search-result excerpt, because the page itself returned HTTP 403 to the fetcher.

---

## 1. Who should be allowed to create and publish servers (separation of duties, review before publishing, four-eyes)

### Takeaway
Every major host platform limits who can *publish* MCP integrations org-wide to an admin or owner tier, and separates "connect to a published server" (any member) from "add or publish a server" (privileged role). OpenAI is the most explicit: a draft-then-publish flow where admins pick allowed actions and write actions trigger safety warnings. No vendor or spec source documents a true two-person (four-eyes) approval for MCP publishing, so web-agent would be going beyond what the platforms do today. Mature change-management practice would still justify it for external audiences and destructive tools.

### Cited Findings
- **Anthropic (Claude Team):** "only Owners and Primary Owners can add [custom connectors] to Team plans." On Enterprise, Owners, Primary Owners and people with a custom role that includes *Manage access to Libraries* can add them. Members then "individually connect to and enable that connector." [primary] — [Claude Help: Get started with custom connectors using remote MCP](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)
- **Anthropic managed authorization:** admins authorize a connector once for the organization under Organization settings > Connectors > Managed authorization, after confirming the IdP connection (Okta at present) and running a test before turning it on. Admins choose which roles inherit it (built-in roles as a group, or individual custom roles), so a pilot can be limited to one custom role. Article dated 24 Aug 2026; GA on Team and Enterprise. [primary] — [Claude Help: Authorize MCP connectors for your entire organization](https://support.claude.com/en/articles/15537633-authorize-mcp-connectors-for-your-entire-organization)
- **OpenAI (ChatGPT Business/Enterprise/Edu):** "only admins/owners can publish MCP apps after testing." Admins publish from Workspace settings → Apps → Drafts → Publish, and are told to "Review safety warnings (especially for write actions)." On Enterprise/Edu, admins can use RBAC to grant selected members permission to create connections to custom MCP servers and to manage workspace access to apps. [snippet-only; the help page returned 403] — [OpenAI Help: Creating custom MCP apps in ChatGPT](https://help.openai.com/en/articles/12584461-creating-custom-mcp-apps-in-chatgpt)
- **OpenAI, default state:** apps and connectors are disabled by default on Enterprise/Edu, and admins must enable them, configure RBAC and set MCP actions. Full MCP support including write actions was rolling out "in beta" to Business, Enterprise and Edu. [snippet-only] — [ChatGPT Enterprise and Edu release notes](https://help.openai.com/en/articles/10128477-chatgpt-enterprise-and-edu-release-notes)
- **OpenAI public app/plugin directory (external publishing):** "All plugin submissions must come from verified individuals or organizations." Identity and business affiliation are verified in the Platform Dashboard. "Trial or demo plugins will not be accepted." Authenticated servers must supply a working demo account. Skills are automatically scanned. [primary, undated page] — [OpenAI Apps SDK: App submission guidelines](https://developers.openai.com/apps-sdk/app-submission-guidelines)
- **OpenAI review in practice:** developers report individual MCP tools in a submission flagged "needs further review before it can go live" without explanation ([community thread](https://community.openai.com/t/mcp-tools-marked-needs-further-review-without-details-what-s-the-next-step/1404421)). OpenAI's own roundup says resubmitting an app moved back to draft "now correctly creates a fresh reviewable item," and the submission form now requires tool-annotation explanations ([App Submission Flow Improvements Roundup](https://community.openai.com/t/app-submission-flow-improvements-roundup/1379047)). These are forum posts and therefore anecdotal.
- **Cloudflare MCP server portals:** admins add servers under Zero Trust > Access controls > MCP Portals. "The account that completes upstream OAuth becomes the server's admin credential," which means the person registering the server also supplies the standing credential. [primary, page last updated 26 Oct 2026] — [Cloudflare docs: MCP server portals](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/)
- **GitHub Copilot:** enterprise owners (or org owners) set the MCP registry URL and the "Allow all" / "Registry only" policy. "Registry only: Only servers from the registry may run." So publishing to the registry is the gate. [primary] — [GitHub Docs: Configure MCP server access](https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-mcp-usage/configure-mcp-server-access)
- **Thoughtworks Technology Radar (Vol. 33, Nov 2025):** "Naive API-to-MCP conversion" is on **Hold**. Internal APIs often expose sensitive data or allow destructive operations, and wrapping them as MCP leaves no reliable way to stop an agent misusing them. Thoughtworks recommends a purpose-built MCP server on top of existing APIs. — [Thoughtworks Radar: Naive API-to-MCP conversion](https://www.thoughtworks.cn/radar/techniques/naive-api-to-mcp-conversion)
- **OWASP GenAI Security Project, "A Practical Guide for Securely Using Third-Party MCP Servers" v1.0 (Oct 2025):** its mitigations include "governance workflows," least privilege and human-in-the-loop oversight. A secondary summary names GRC leaders "needing auditable control over which servers and tools agents may use" as an audience. — [OWASP GenAI cheatsheet resource page](https://genai.owasp.org/resource/cheatsheet-a-practical-guide-for-securely-using-third-party-mcp-servers-1-0/); [AIGL summary](https://www.aigl.blog/a-practical-guide-for-securely-using-third-party-mcp-servers-owasp-genai-security-project-v1-0-oct-23-2025/)
- **Harmonic Security (third-party guidance for Claude Cowork):** recommends allowing only admin-approved connectors, and setting write tools such as send_email and post_message to Blocked per tool "unless explicitly justified." [secondary] — [Harmonic: Securing Claude Cowork](https://www.harmonic.security/resources/securing-claude-cowork-a-security-practitioners-guide)

### Inferences
- The common pattern is two roles: a **creator/maintainer** who builds and tests the draft, and a **publisher** (admin or owner) who makes it live. Web-agent can copy this. Separate creator from approver when the server (a) targets any external audience (Clients, Partners, Resellers), (b) includes any tool annotated `destructiveHint: true` or `readOnlyHint: false`, or (c) widens dataset or tool scope on an already-published server. Internal-only, read-only servers could use single-approver publishing.
- Cloudflare's "whoever completes OAuth becomes the admin credential" pattern is a separation-of-duties anti-pattern. Web-agent servers should run tools under a service identity that the publishing workflow controls, not under the creator's personal token.
- Thoughtworks' Hold supports making the tool allowlist an explicit, reviewed selection from a curated catalog, rather than auto-exposing every catalog tool. Web-agent's UX already works this way.
- OpenAI separates permission to *create* connections from permission to *publish*. That suggests two distinct admin permissions (the red-marked admin entry points), not one "admin" flag.

### Gaps
- No vendor or spec source describes **four-eyes (two-person) approval** for publishing an MCP server. Claude, ChatGPT, GitHub and Cloudflare all allow one admin to publish. Any four-eyes requirement in the ADR would come from general change-management or SOX-style practice, not MCP-specific precedent.
- I could not retrieve OpenAI's help-center pages directly (HTTP 403). OpenAI claims above come from search-result excerpts of those pages and should be checked by hand.
- I did not read the OWASP PDF itself, so I cannot quote its specific approval-workflow text.

## 2. Tool catalog governance: vetting, ownership, risk classification, supply chain, the official MCP Registry, and server cards

### Takeaway
The official MCP Registry (preview since 8 Sep 2025, still preview in Oct 2026) is a public metadata and namespace service only. It verifies who owns a namespace, makes published versions immutable and delegates security scanning elsewhere. It explicitly does not host private servers and recommends a private registry that implements its OpenAPI spec. Tool risk classification is converging on MCP tool annotations (`readOnlyHint`, `destructiveHint`, `openWorldHint`), which OpenAI now requires as explicit booleans. Server Cards (SEP-2127, accepted Aug 2026) add pre-connection discovery, but the `.well-known` path is still unsettled.

### Cited Findings
**Official MCP Registry**
- Status: "The MCP Registry is currently in preview. Breaking changes or data resets may occur before general availability." It is backed by contributors including Anthropic, GitHub, PulseMCP and Microsoft. [primary] — [MCP Registry: About](https://modelcontextprotocol.io/registry/about)
- Preview launched 8 Sep 2025 at registry.modelcontextprotocol.io. — [MCP blog: Introducing the MCP Registry (2025-09-08)](https://blog.modelcontextprotocol.io/posts/2025-09-08-mcp-registry-preview/)
- I found no official GA announcement. A Workato "MCP Registry — Now Generally Available" changelog is about Workato's own product, not the official registry. — [Workato changelog](https://www.workato.com/product-hub/changelog/mcp-registry-now-generally-available/)
- Namespace verification: server names use reverse-DNS form (`io.github.username/server`, `com.example/server`) tied to verified GitHub accounts or domains. "Publishers must verify ownership of their namespace through GitHub, DNS, or HTTP challenges." [primary] — [MCP Registry: About](https://modelcontextprotocol.io/registry/about)
- Private servers: "The MCP Registry **does not** support private servers… If you want to publish private servers, we recommend that you host your own private MCP registry." Public remote servers qualify if "publicly accessible (e.g., a remote server that is not restricted to private networks)." [primary] — same source
- Security scanning is delegated to package registries (npm, PyPI, Docker Hub) and downstream aggregators. "The MCP Registry focuses on namespace authentication and metadata hosting." Maintainers can manually take down spam or malicious servers under a moderation policy. [primary] — same source
- Intended consumers: "The MCP Registry is not intended to be directly consumed by host applications." Hosts should consume downstream registries that expose the official OpenAPI spec. Aggregators are expected to poll "once per hour." The official codebase "is **not** designed for self-hosting." [primary] — same source
- server.json holds a unique name, location (package or remote URL), execution instructions, and description and capabilities. [primary] — same source
- Version immutability: "The version string **MUST** be unique for each publication of the server. Once published, the version string (and other metadata) cannot be changed." Version ranges are prohibited and semver is recommended. "For remote servers with an API version, the server version should align with the API version," with the example URL `https://api.myservice.com/mcp/v2.1`. [primary] — [MCP Registry: Versioning](https://modelcontextprotocol.io/registry/versioning)

**Server Cards and `.well-known` discovery**
- SEP-1649 (an issue, authored by Anthropic staff) proposed that HTTP-based MCP servers expose a server card at a `.well-known` URI. — [SEP-1649 issue](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/1649)
- SEP-2127 "MCP Server Cards – HTTP Server Discovery" (PR by dsp-ant, opened 21 Jan 2026) supersedes it. The PR is merged, and a comment says core maintainers voted to accept it on 13 Aug 2026. Candidate fields include name, description, title, version, repository, icons, remotes (with `supportedProtocolVersions` and `authentication` moved inside), packages, capabilities, resources, tools, prompts and `_meta`. The card is proposed as a strict subset of server.json, and follow-up PR #2186 clarified that relationship. The path changed during discussion (`.well-known/ai-catalog.json` → `.well-known/mcp/server-cards.json`), and a later comment said the card "is not at a generic well-known URI and needs an AI Catalog to point to it." Whether `tools` may be marked "dynamic" was contested. — [SEP-2127 PR](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2127)
- Secondary sources disagree on the published path (`/.well-known/mcp.json` vs `/.well-known/mcp/server-cards.json`) and mention a competing lighter proposal, SEP-1960 (`/.well-known/mcp`). — [Bex blog (Jul 2026)](https://bex.co/blog/2026/07/08/mcp-server-cards-well-known-discovery); [mcpplaygroundonline](https://mcpplaygroundonline.com/blog/mcp-server-cards-well-known-discovery)

**Risk classification via annotations**
- OpenAI requires `readOnlyHint`, `destructiveHint` and `openWorldHint` set "to explicit boolean values (true or false)." `destructiveHint: true` covers deletion, overwriting, cancellation, access revocation and irreversible sends or transactions. "Being able to undo an action does not, by itself, justify setting destructiveHint to false." "Annotations inform client safeguards; they do not grant permission." [primary] — [OpenAI App submission guidelines](https://developers.openai.com/apps-sdk/app-submission-guidelines)
- OpenAI workspace admins have per-app approval levels: Always ask, Any changes, Important actions (the default: reads run automatically, consequential writes need confirmation) and Never ask, which OpenAI flags as elevated risk. [secondary] — [Strac: ChatGPT Connectors admin guide](https://www.strac.io/blog/chatgpt-connectors)

**Private registries and inventories in enterprises**
- Azure API Center can "maintain an inventory (or registry) of remote or local model context protocol (MCP) servers." Admins register via Inventory > Assets > Register an asset > MCP server, entering title, summary, description, use cases and remote runtime URLs. A preview "Discover > MCP" feature adds ready-made servers in one click, and registered servers can feed Microsoft Foundry tool catalogs. [primary] — [Microsoft Learn: Register and discover MCP servers in API Center](https://learn.microsoft.com/en-us/azure/api-center/register-discover-mcp-server)
- Microsoft markets API Center as "a unified MCP tools registry with integration into Microsoft Foundry and Microsoft Copilot Studio." [primary marketing] — [Azure API Management product page](https://azure.microsoft.com/en-us/products/api-management)
- GitHub Copilot accepts an API Center registry URL in the form `https://SERVICE-NAME.data.REGION.azure-apicenter.ms/workspaces/WORKSPACE-NAME`, without `/v0.1/servers`, because Copilot appends the MCP v0.1 path itself. [primary] — [GitHub Docs: Configure MCP server access](https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-mcp-usage/configure-mcp-server-access)

**Supply-chain and drift controls**
- An OWASP slide deck recommends trust-on-first-use validation that alerts administrators "whenever a new tool is added or if an existing tool's description changes." — [OWASP Stuttgart chapter: All About MCP Security (25 Sep 2025)](https://owasp.org/www-chapter-stuttgart/assets/slides/2025-09-25_All_About_MCP_Security.pdf)
- Anthropic warns: "Custom connectors allow you to connect Claude to arbitrary services that have not been verified by Anthropic," and "Server developers may update tool behavior unexpectedly, leading to unintended or malicious behavior." [primary] — [Claude Help: custom connectors](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)
- OpenAI does not vet custom MCP servers; customers must vet them. [secondary] — [Strac](https://www.strac.io/blog/chatgpt-connectors); [Obot](https://obot.ai/resources/learning-center/chatgpt-mcp-support-enterprise/)

### Inferences
- For web-agent, the internal tool catalog is effectively a **private MCP registry**. Each catalog tool should carry an owner (team or person), a risk tier derived from the three annotations plus the data classes it touches, a review date, and provenance (first-party code or third-party package/server with a pinned version). Tools with `destructiveHint: true` or `openWorldHint: true` should be barred from external-audience servers unless an additional approval is recorded.
- Annotations are self-declared hints ("they do not grant permission"). Catalog vetting should verify that each declared annotation matches the tool's actual behavior. It should not trust the annotation alone.
- Because `https://webagent.dev/mcp/<slug>` servers are remote and publicly reachable, they *could* be listed in the official registry under a DNS-verified `dev.webagent/<slug>` namespace. Client-specific or partner-specific servers are effectively "private servers" in the registry's sense and belong only in web-agent's own catalog. Exposing that catalog via the registry's OpenAPI shape (`/v0.1/servers`) would let customers point GitHub Copilot or API Center at it. Whether to do this is an ADR option, not a requirement.
- Server cards are worth tracking, but the ADR should not commit to a `.well-known` path until the spec's final location is confirmed.

### Gaps
- I could not confirm the final normative `.well-known` path or field list for Server Cards from merged spec text. Only PR discussion and secondary blogs were read.
- I did not read the registry's Moderation Policy or Authentication pages in full. The registry's handling of "deprecated" or "deleted" status for versions was not confirmed from primary text.
- No primary source on how large SaaS vendors assign *tool ownership* or run periodic tool re-certification for MCP.

## 3. Change management: versioning tool sets and descriptions, list_changed, rug pulls, staged rollout, re-approval, immutable URLs

### Takeaway
MCP spec revision 2026-07-28 makes change propagation more explicit: opt-in `subscriptions/listen` for `toolsListChanged`, cache hints (`ttlMs`, `cacheScope`) on `tools/list`, deterministic tool ordering, and server identity on every result. The protocol still does not pin or sign tool definitions, so "rug pull" protection is a client or gateway responsibility. A community SEP for mandatory description pinning (SEP-3452) was opened and closed on process grounds in late Oct 2026. Platforms handle change conservatively: OpenAI lands new actions deselected, Anthropic makes admins remove and re-add a connector to edit it, and Cloudflare auto-enables new upstream tools unless allowlist mode is on. The registry treats each published version as immutable and recommends version-aligned remote URLs.

### Cited Findings
**Spec revision 2026-07-28 (changelog served at /specification/latest)**
- List endpoints (`tools/list`, `resources/list`, `prompts/list`) "no longer vary per-connection" now that protocol-level sessions and `Mcp-Session-Id` are removed (SEP-2567). — [MCP spec changelog](https://modelcontextprotocol.io/specification/latest/changelog)
- `subscriptions/listen` replaces the HTTP GET stream. Clients opt in to `toolsListChanged`, `promptsListChanged`, `resourcesListChanged` and `resourceSubscriptions`, and notifications carry `io.modelcontextprotocol/subscriptionId` (SEP-2575). — same source
- `tools/list` results must include `ttlMs` (a freshness hint) and `cacheScope` (`"public"` or `"private"`, controlling whether shared intermediaries may cache) via `CacheableResult`. "Both fields complement existing `listChanged` notifications" (SEP-2549). — same source
- "Servers **SHOULD** return tools from `tools/list` in a deterministic order." — same source
- Servers SHOULD identify themselves in each result's `_meta` (`io.modelcontextprotocol/serverInfo`), and a mandatory `server/discover` RPC advertises versions, capabilities and identity (SEP-2575). — same source
- Governance: the spec adopted a feature lifecycle policy with Active, Deprecated and Removed states, "a minimum twelve-month deprecation window," and a registry of deprecated features (SEP-2596). — same source
- The changelog text still says "introduced in this draft" in one place, and one secondary source calls 2026-07-28 a "release candidate." I did not independently confirm its final ratification date. — [mcpplaygroundonline](https://mcpplaygroundonline.com/blog/mcp-server-cards-well-known-discovery) (secondary)

**Rug pulls and pinning**
- SEP-3452, "Mandatory tool definition integrity — description pinning and content validation," opened 24 Oct 2026 by Nicholas Michael Kloster. It proposes that clients store a SHA-256 of each tool description, compare after `tools/list_changed`, "MUST NOT silently accept a changed description," and require re-approval. It also asks servers to include a human-readable `reason` in the `_meta` of `tools/list_changed`. The issue was closed on 26 Oct 2026 by maintainer localden on process grounds (SEPs need working-group engagement first), with no technical ruling. Community feedback: pin `inputSchema`, `annotations`, `title` and server `instructions`, not only `description`; use a canonical serialization such as JCS (RFC 8785); align with earlier digest proposal #1766; bind in-flight calls to the definition pinned when the call began. — [SEP-3452 issue](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/3452)
- Secondary sources agree the protocol has no signature, no version that clients must pin and no mandatory change notification. The common defense is hashing the approved definition and requiring re-approval on mismatch. — [Pluto Security glossary](https://pluto.security/glossary/mcp-rug-pull-attack/); [dev.to: MCP Tool Drift](https://dev.to/alex_spinov/mcp-tool-drift-pin-the-manifest-block-rug-pulls-in-40-lines-4mlp); [SecureW2](https://securew2.com/blog/mcp-rug-pull-attack)

**How platforms handle upstream change**
- **OpenAI:** admins use "Configure Actions" to select or deselect allowed actions, and "Refresh to pull new actions (deselected by default)." Actions can also be changed after publishing. [snippet-only] — [OpenAI Help: Creating custom MCP apps](https://help.openai.com/en/articles/12584461-creating-custom-mcp-apps-in-chatgpt). A third-party guide describes published apps as running on a frozen tool snapshot, while another excerpt says Business apps "cannot be updated after publishing" at launch. These conflict and are unverified. — [Elaichi](https://elaichi.ai/blog/restrict-chatgpt-enterprise-connectors/)
- **Anthropic:** "To edit a connector, you'll need to remove it first, then re-add it using the updated details." No automatic re-approval on server-side tool changes is described. [primary] — [Claude Help: custom connectors](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)
- **Cloudflare portals:** servers using dynamic client registration (DCR) sync tools and prompts "about every two hours," and admins can sync manually. "New tools are enabled by default unless the allowlist mode is on" (`default_disabled`). Renaming a tool upstream drops the admin's alias. Servers with manual OAuth capture tools only at first user authorization. No formal approval workflow exists for new upstream tools. [primary] — [Cloudflare MCP portals](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/)
- **OpenAI directory:** "Previously approved plugins that are later found in violation may be removed," and "hidden behavior… may result in removal." The guidelines do not say whether tool changes after approval require resubmission. [primary] — [OpenAI App submission guidelines](https://developers.openai.com/apps-sdk/app-submission-guidelines)
- **Registry:** each published version is immutable, and remote server versions should align with an API-versioned URL (e.g. `/mcp/v2.1`). [primary] — [MCP Registry: Versioning](https://modelcontextprotocol.io/registry/versioning)

### Inferences
- **Version the server manifest, not the URL.** Treat each publish as an immutable version: tool IDs, tool description text, input/output schema hash, annotations, dataset scope and audiences. Keep `https://webagent.dev/mcp/<slug>` stable as the canonical URL, and optionally expose `/mcp/<slug>/v<N>` for clients that want to pin. The registry's "align version with remote API version" guidance supports offering both.
- **Classify changes the way OpenAI does.** Removing a tool, narrowing scope or fixing a typo is low risk and can auto-publish with notice. Adding a tool, widening dataset scope, changing any annotation toward write or destructive, adding an audience, or materially changing a description is scope growth. Scope growth should go back through approval and arrive *disabled for connected clients until re-approved*, mirroring OpenAI's "new actions deselected by default."
- **Notification mechanics under 2026-07-28.** Emit `toolsListChanged` only to clients that opted in through `subscriptions/listen`. Set a modest `ttlMs` on `tools/list`, because it bounds how stale a client's tool list can be, and use `cacheScope: "private"` if lists vary by caller. Return tools in deterministic order. Include `serverInfo.version` in result `_meta` so clients and logs can attribute calls to a manifest version.
- **"List endpoints no longer vary per-connection" matters for audience design.** If different audiences (Internal, Clients, Partners, Resellers) need different tool sets, the safer design is distinct published servers or slugs per audience, or per-principal authorization at call time, rather than relying on per-session list filtering. This needs confirmation with the transport and auth researchers.
- **Staged rollout:** publish a new version to the Internal audience (or a canary group) first, watch error and destructive-call metrics for a set period, then promote to external audiences. No MCP-specific source prescribes this; it is standard progressive-delivery practice.
- **Rug-pull defense from the publisher's side:** web-agent is the server operator, so the main risk is *our own* silent drift. The publish pipeline should refuse to serve a description or schema that differs from the approved manifest hash. This is the server-side mirror of SEP-3452. Hash the full definition (name, description, inputSchema, outputSchema, annotations) with a canonical serialization such as JCS, as SEP-3452 commenters recommended.
- Hashing a tool's definition does not detect a change in the code behind it. Catalog tool implementations therefore also need code review and pinned versions.

### Gaps
- No primary source on how Claude or ChatGPT clients *react* to `toolsListChanged` from a remote connector (auto-refresh, prompt the user, or ignore).
- I found no vendor documentation describing staged or canary rollout specifically for MCP tool sets.
- The final status of the 2026-07-28 revision (RC vs. final) was not independently confirmed.
- I could not retrieve OpenAI primary text resolving the "frozen snapshot" vs "cannot be updated" conflict.

## 4. Operations: observability, cost and budgets, quotas, anomaly alerting, kill switches, revocation, incident response, deprecation and retirement

### Takeaway
OpenTelemetry has MCP semantic conventions (status: Development) with standard span attributes and duration metrics, and the 2026-07-28 spec formalizes trace propagation through `_meta` and pushes logging toward OpenTelemetry. Gateways (Cloudflare, Kong, Pomerium, Azure API Management) supply per-tool logs, rate limits and revocation. MCP-specific guidance on **cost budgets, anomaly alerting and incident runbooks is thin**, so the ADR will have to compose these from general practice. For retirement, the spec's own 12-month deprecation policy is the best in-ecosystem analog.

### Cited Findings
**Observability standards**
- The OTel MCP semantic conventions moved to the `semantic-conventions-genai` repository. Status is **Development**. Span name is `{mcp.method.name} {target}`, where target is the tool or prompt name. `mcp.method.name` is required. Recommended attributes: `gen_ai.operation.name` (`execute_tool` for tool calls), `mcp.protocol.version`, `mcp.session.id`, `network.transport`. Conditionally required: `gen_ai.tool.name`, `error.type`, `jsonrpc.request.id`, `rpc.response.status_code`. Opt-in only, because they may contain sensitive data: `gen_ai.tool.call.arguments`, `gen_ai.tool.call.result`. [primary] — [OTel semconv-genai: MCP](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/mcp.md); [opentelemetry.io redirect page](https://opentelemetry.io/docs/specs/semconv/gen-ai/mcp/)
- Metrics named: `mcp.client.operation.duration`, `mcp.server.operation.duration`, `mcp.client.session.duration`, `mcp.server.session.duration`. `mcp.client.operation.duration` is a histogram in seconds, with recommended bucket boundaries 0.01 to 300 s and attributes `mcp.method.name` (required) and `gen_ai.tool.name` and `error.type` (conditional). [primary] — [OTel semconv-genai: MCP](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/mcp.md)
- Trace context goes in `params._meta` as unprefixed `traceparent`, `tracestate` and `baggage` keys (SEP-414, now documented in the 2026-07-28 spec). [primary] — [MCP spec changelog](https://modelcontextprotocol.io/specification/latest/changelog)
- The spec deprecates the Logging feature (SEP-2577) and suggests logging "to `stderr` (stdio) or use OpenTelemetry instead." [primary] — same source
- Streamable HTTP POSTs must carry `Mcp-Method` and `Mcp-Name` headers (SEP-2243). [primary] — same source

**Gateway-level operations**
- **Cloudflare portals:** portal logs (time, status, server, capability, duration) per portal or server; Logpush export to a SIEM on Enterprise plans; an API returning daily or monthly tool-call counts; DLP on tool requests *and* responses when traffic goes through Gateway. Revocation: user sign-out revokes portal OAuth grants and upstream state; admins can reauthenticate a server, turn servers off and delete portals via API. "Admin tokens can expire silently… admins aren't notified," so Cloudflare recommends periodic status checks. [primary] — [Cloudflare MCP portals](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/)
- **Kong:** MCP is handled through plugins that require Kong Gateway 3.12+ and the AI Gateway Enterprise tier, with per-consumer tool ACLs and Kong's existing rate-limiting plugins. [secondary] — [Obot: 13 best MCP gateways](https://obot.ai/blog/the-13-best-mcp-gateways-for-enterprise-teams/)
- **Docker MCP Gateway:** enables or disables tools per profile, with logging and call tracing, and is positioned for local and developer use rather than org-wide governance. [secondary] — [Maxim: Docker MCP Gateway alternatives](https://www.getmaxim.ai/articles/top-5-docker-mcp-gateway-alternatives-for-production-teams-in-2026/)
- **Pomerium:** "enforces authorization policies on every request, including fine-grained tool-level access control," and logs every tool call. A vendor blog lists audit fields: agent identity, tool name, method, parameters, response status and the authorization decision. [primary docs + vendor blog] — [Pomerium docs: MCP](https://www.pomerium.com/docs/capabilities/mcp); [Pomerium blog](https://pomerium.com/blog/top-5-agentic-gateways-for-securing-mcp-tool-calls-in-2026)
- **Lasso:** an open-source (MIT) self-hosted proxy focused on content inspection (secret masking, PII detection via Presidio, injection filtering) rather than deterministic per-tool authorization. [secondary] — [PolicyLayer comparison](https://policylayer.com/compare/lasso-security); [Lasso use case page](https://lasso.security/use-cases/mcp-security)
- **Azure:** "Azure API Management governs MCP traffic (security, rate limiting, monitoring) — the runtime gateway in the data path. Azure API Center governs MCP discovery (inventory, metadata, portal)." [secondary] — [Microsoft devblog: Locking down MCP with API Center](https://devblogs.microsoft.com/all-things-azure/locking-down-mcp-create-a-private-registry-on-azure-api-center-and-enforce-it-in-github-copilot-and-vs-code/)

**Kill switches and revocation at host platforms**
- **Claude managed authorization:** deprovisioning a user in the IdP removes their connector access, and sessions end when the access token expires or is revoked. Admins can require IdP-only connection. [primary] — [Claude Help: Authorize MCP connectors for your org](https://support.claude.com/en/articles/15537633-authorize-mcp-connectors-for-your-entire-organization)
- **GitHub Copilot "Registry only":** the policy takes effect "immediately," so removing a server from the registry acts as an org-wide kill switch in supported IDEs. GitHub says the registry policy "is in public preview and is not the recommended method for restricting access to MCP servers," and recommends `managed-settings.json` instead. [primary] — [GitHub Docs: Configure MCP server access](https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-mcp-usage/configure-mcp-server-access)
- A secondary source says GitHub's enforcement matches only server names or IDs, so it can be bypassed by editing configuration. [secondary, unverified] — [NeuralTrust](https://neuraltrust.ai/blog/mcp-registry-allowlist-enterprise)
- **Atlassian (as an MCP server publisher):** "key MCP events, such as tool invocations and first-time app installs" are written to the org audit log. [primary blog] — [Atlassian: Rovo MCP GA](https://www.atlassian.com/blog/announcements/atlassian-rovo-mcp-ga)

**Deprecation and retirement**
- MCP spec feature lifecycle: Active → Deprecated → Removed, with "a minimum twelve-month deprecation window" and a public registry of deprecated features (SEP-2596). [primary] — [MCP spec changelog](https://modelcontextprotocol.io/specification/latest/changelog)
- Registry versions cannot be edited after publishing, so retirement happens by publishing status changes or new versions, not by editing old ones. [primary] — [MCP Registry: Versioning](https://modelcontextprotocol.io/registry/versioning)

### Inferences
- **Instrumentation:** emit OTel spans and metrics using the MCP semconv names (`mcp.server.operation.duration`, `gen_ai.tool.name`, `error.type`). Add web-agent attributes for `server.slug`, `server.version` (manifest version), `audience`, `tenant/org`, `principal`, the tool's `destructive` and `readOnly` flags, rows or bytes returned, and estimated cost. Do not log tool arguments or results by default; OTel itself marks them opt-in because they are sensitive. Because `Mcp-Method` and `Mcp-Name` are now HTTP headers, per-tool rate limiting and metering can run at the edge (Vercel middleware or firewall) without parsing JSON bodies.
- **Session metric mismatch:** the OTel conventions still include `mcp.session.id` and session-duration metrics, but spec 2026-07-28 removed protocol sessions. Expect the semconv to change, and do not build dashboards that depend on session IDs.
- **Quotas and budgets:** treat per-person daily call limits and the monthly budget as policy enforced at the server or gateway, with three tiers: soft warning (for example 80%), hard stop (100%), and an admin override that leaves an audit trail. Return a structured MCP error, not a silent failure, so clients can show the reason.
- **Anomaly alerting signals:** destructive-call rate per principal or tenant against baseline, data volume returned per call and per day, new-principal bursts, error-rate spikes after a version publish (a rollback trigger), calls arriving from audiences or tenants not expected for that server, and calls to tools that have since been deprecated.
- **Kill-switch tiers:** per tool (disable one tool across all servers), per server version (roll back to the previous immutable manifest), per server (unpublish: return a clear error and drop it from the catalog), per audience or tenant (revoke grants for one partner), and per principal (revoke tokens). Cloudflare's "admin tokens expire silently" warning argues for health checks on any upstream credential a server depends on.
- **Retirement:** mark deprecated → announce with a date → stop new connections while existing ones still work → return an explicit "server retired" error at the URL → keep the slug reserved so it is never reused (an immutable published URL). The spec's 12-month window is a reasonable ceiling for external audiences; internal servers can use a shorter one.

### Gaps
- No primary source gives MCP-specific **cost-tracking or budget** practice. Vendors document rate limits, not cost budgets per server or per person.
- No MCP-specific **incident response playbook** was found from Anthropic, OpenAI, Microsoft, OWASP or CoSAI. I did not read the OWASP PDFs in full.
- I did not find OTel semconv units or attributes for the server-side metrics beyond their names (the text was truncated).
- The claim that Microsoft Advanced Connector Policies went GA in June 2026 is from a single secondary blog and is unverified ([StackOne](https://www.stackone.com/blog/best-mcp-gateway-for-copilot-studio/)).

## 5. How platforms and vendors govern MCP today, and what customers' admins expect

### Takeaway
All three big host ecosystems now offer org-admin gating: Anthropic (role-scoped managed authorization, domain restriction, owner-only custom connectors), OpenAI (admin-published apps, RBAC, per-action configuration) and Microsoft/GitHub (registry-based allowlists, API Center as a private registry, Power Platform data policies). Gateways add per-tool allowlists, logs and DLP. Customers' admins expect to see an admin-approved catalog, decide which roles or groups get which server, approve individual tools (especially writes), revoke access instantly through their IdP, and get audit logs exportable to a SIEM.

### Cited Findings
**Anthropic (Claude)**
- Custom connectors: owner-only on Team; Owners, Primary Owners or a custom role with *Manage access to Libraries* on Enterprise. Members connect individually. Owners can "disable specific tool calls that render interactive connectors." Users can disable tools in "Search and tools." In Research mode, "Claude can invoke tools from your connectors automatically without further approval," and Anthropic advises disabling write-capable tools there. [primary] — [Claude Help: custom connectors](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)
- Managed authorization (24 Aug 2026, GA Team and Enterprise): role-scoped inheritance, scopes narrowed per role, IdP-only connection option, deprovisioning through the IdP. No per-tool allow/ask/block or audit log is described in that article. [primary] — [Claude Help: Authorize MCP connectors for your org](https://support.claude.com/en/articles/15537633-authorize-mcp-connectors-for-your-entire-organization)
- "Restrict verified-domain connectors to your Enterprise" (Enterprise only): blocks accounts outside the Enterprise from connecting supported services (Gmail, Slack, M365, Notion, Box, Atlassian) with a verified-domain email. Configurable by Owners, Primary Owners or custom roles with Identity & Access = Manage. Existing connections are not cut, and admins are not notified of blocked attempts. [primary] — [Claude Help: Restrict verified-domain connectors](https://support.claude.com/en/articles/15402193-restrict-verified-domain-connectors-to-your-enterprise)
- Claude Code: `allowedMcpServers` plus `allowManagedMcpServersOnly` act as an authoritative catalog filter. "Allowlists filter servers but don't register them." [primary] — [Claude Code Docs: Control MCP server access](https://code.claude.com/docs/en/managed-mcp)
- A user-filed issue reports that on Claude Teams, custom MCP connectors with shared credentials expose those credentials to all team members, with no per-user scoping. This is unconfirmed by Anthropic. — [GitHub issue anthropics/claude-code #44980](https://github.com/anthropics/claude-code/issues/44980)

**OpenAI (ChatGPT)**
- Admin- or owner-only publishing, RBAC for who may create connections, Configure Actions with refreshed actions deselected by default, and post-publish action control. [snippet-only] — [OpenAI Help: Creating custom MCP apps](https://help.openai.com/en/articles/12584461-creating-custom-mcp-apps-in-chatgpt)
- Apps and connectors are off by default on Enterprise/Edu, and write actions are in beta. [snippet-only] — [Enterprise/Edu release notes](https://help.openai.com/en/articles/10128477-chatgpt-enterprise-and-edu-release-notes)
- Enterprise compliance logs export conversation and audit events to SIEM and eDiscovery tools. One guide names an admin event `APP_SET_ENABLED_ACTIONS`, which is unverified against OpenAI docs. [secondary] — [Elaichi](https://elaichi.ai/blog/restrict-chatgpt-enterprise-connectors/); [Strac](https://www.strac.io/blog/chatgpt-connectors)
- The public directory requires verified developers, explicit annotations and ongoing compliance, and approved plugins can be removed. [primary] — [OpenAI App submission guidelines](https://developers.openai.com/apps-sdk/app-submission-guidelines); launch context: [OpenAI: Developers can now submit apps to ChatGPT](https://openai.com/index/developers-can-now-submit-apps-to-chatgpt/)

**GitHub (Copilot)**
- Internal MCP registry and allowlist controls: VS Code Insiders on 12 Sep 2025 ([changelog](https://github.blog/changelog/2025-09-12-internal-mcp-registry-and-allowlist-controls-for-vs-code-insiders/)), VS Code Stable public preview on 18 Nov 2025 ([changelog](https://github.blog/changelog/2025-11-18-internal-mcp-registry-and-allowlist-controls-for-vs-code-stable-in-public-preview/)), JetBrains and Eclipse public preview on 28 Oct 2025 ([Microsoft devblog](https://devblogs.microsoft.com/java/mcp-registry-and-allowlist-controls-for-copilot-in-jetbrains-and-eclipse-now-in-public-preview/)). Visual Studio allowlist enforcement was "not yet available" at the time of the VS Code Stable post.
- The "Registry only" policy is still public preview in GitHub Docs, which point to `managed-settings.json` as "the more secure, generally available method." [primary] — [GitHub Docs: Configure MCP server access](https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-mcp-usage/configure-mcp-server-access); [GitHub Docs: Restrict based on registry](https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-mcp-usage/restrict-based-on-registry)

**Microsoft (Azure, Copilot Studio, Power Platform)**
- API Center as an MCP inventory or registry, with a preview "Discover > MCP" feature and a Foundry tool-catalog feed. [primary] — [Microsoft Learn: API Center MCP](https://learn.microsoft.com/en-us/azure/api-center/register-discover-mcp-server)
- Copilot Studio data policies: connectors sit in Business, Non-business or Blocked groups. Data-policy enforcement has applied to all tenants since early 2025 with no agent exemptions. [primary] — [Microsoft Learn: Copilot Studio DLP example 4](https://learn.microsoft.com/en-us/microsoft-copilot-studio/dlp-example-4)
- The Dataverse MCP server is enabled by default for Copilot Studio and can be disabled per environment. [primary] — [Microsoft Learn: Disable Dataverse MCP](https://learn.microsoft.com/en-us/power-apps/maker/data-platform/data-platform-mcp-disable)
- Claims that data policies govern MCP servers and their tools through the connector stack, and that Advanced Connector Policies (with action-level control) went GA in June 2026, come from secondary sources and conflict with Learn pages that still describe the Business/Non-business groups. [secondary, unverified] — [StackOne](https://www.stackone.com/blog/best-mcp-gateway-for-copilot-studio/)
- A Sep 2026 report describes a new Microsoft Copilot plugin registry, with Copilot Studio, GitHub Copilot and Foundry named as *future* targets. [secondary, unverified] — [WindowsForum](https://windowsforum.com/news/microsoft-copilot-plugin-registry-replaces-agents-admin-controls-mcp-security-and-rollout.446725/)

**Gateways** (detail in section 4)
- Cloudflare MCP portals: per-portal tool allowlist (`default_disabled`), Access policies, logs, Logpush and DLP. [primary] — [Cloudflare docs](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/)
- Pomerium (per-tool authorization and audit), Kong (tool ACLs and rate limits, enterprise tier), Docker (developer-local profiles) and Lasso (content inspection) are covered above. Comparison overviews: [Obot](https://obot.ai/blog/the-13-best-mcp-gateways-for-enterprise-teams/), [StackOne](https://www.stackone.com/blog/best-mcp-gateways/) (secondary).

### Inferences
- **What customer admins will expect from web-agent's servers, based on what their host platforms already give them:**
  1. A stable identity and URL they can allowlist (Claude Code `allowedMcpServers`, GitHub "Registry only", Cloudflare portals). Publishing immutable URLs and versioned metadata helps.
  2. Accurate, explicit annotations on every tool. OpenAI's "Important actions" approval default and Anthropic's guidance to disable write tools in Research mode both depend on them.
  3. Least-privilege OAuth scopes that their IdP can narrow and revoke (Claude managed authorization narrows scopes per role).
  4. Stable tool names. Cloudflare drops aliases when tools are renamed, and OpenAI lands new actions disabled, so renames and additions create work for customers' admins.
  5. Audit evidence they can export.
- Publishing web-agent servers in an OpenAPI-compatible registry shape, and optionally to the official registry under a DNS-verified namespace, lowers adoption friction for customers who use GitHub Copilot or API Center allowlists.

### Gaps
- Google (Gemini Enterprise or Workspace) admin controls for MCP were not researched within the tool-call budget.
- I could not confirm whether Claude Enterprise offers org-level per-tool allow/ask/block for *custom* connectors. The articles read did not describe it.
- I found no Gartner or Forrester public summaries. Thoughtworks Radar Vol. 34 (Apr 2026) MCP blips were not read ([PDF](https://www.thoughtworks.com/content/dam/thoughtworks/documents/radar/2026/04/tr_technology_radar_vol_34_en.pdf)).

## 6. Customer-facing governance: what client and partner admins need, and contract or terms implications

### Takeaway
SaaS vendors that publish MCP servers (Atlassian is the clearest documented example) give *customer* org admins controls over which AI clients and domains may connect, whether API-token access is allowed, IP allowlists, and audit logs of tool invocations. Host platforms likewise put the vetting burden on the customer ("not verified by Anthropic"; OpenAI customers must vet custom apps). I found no primary sources on contract or terms language for exposing data via MCP to resellers or partners. That part of the ADR rests on inference and legal review.

### Cited Findings
- **Atlassian Rovo MCP server (customer-admin controls):** admins can turn off "Allow Atlassian supported domains," add or remove custom trusted domains ("You can remove domains from your organization to prevent AI tools from accessing your apps"), and toggle API-token authentication. Domain blocking works only for OAuth 2.1 clients, not API-token clients. IP allowlists are enforced per Atlassian app. The page advises "Use least privilege, review high-impact changes before confirming." It describes no single org-wide off switch and no per-tool read/write toggle. [primary] — [Atlassian Support: Control Atlassian Rovo MCP server settings](https://support.atlassian.com/security-and-access-policies/docs/control-atlassian-rovo-mcp-server-settings/)
- Atlassian logs "key MCP events, such as tool invocations and first-time app installs" in the org audit log. [primary] — [Atlassian: Rovo MCP GA](https://www.atlassian.com/blog/announcements/atlassian-rovo-mcp-ga)
- A vendor blog describes Atlassian's domain allowlist as a de facto kill switch, because removing a domain revokes new OAuth connections. [secondary] — [TrueFoundry](https://www.truefoundry.com/blog/atlassian-mcp-server)
- **Claude:** for Enterprise admins, the problem is keeping corporate identities out of personal Claude accounts ("Restrict verified-domain connectors"), and the article says this "doesn't replace data loss prevention" and does not notify admins. [primary] — [Claude Help](https://support.claude.com/en/articles/15402193-restrict-verified-domain-connectors-to-your-enterprise)
- **Claude managed authorization** lets the customer's IdP be the revocation point: deprovisioning removes access. [primary] — [Claude Help](https://support.claude.com/en/articles/15537633-authorize-mcp-connectors-for-your-entire-organization)
- **Responsibility allocation:** "Custom connectors allow you to connect Claude to arbitrary services that have not been verified by Anthropic." [primary] — [Claude Help](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp). OpenAI "does not vet the server" and customers must vet custom apps. [secondary] — [Strac](https://www.strac.io/blog/chatgpt-connectors)
- **Cloudflare** gives the operating org per-portal and per-server logs and a tool-call count API (daily or monthly), the kind of usage report a customer admin would want. [primary] — [Cloudflare MCP portals](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/)

### Inferences
- **Customer-admin console (for Clients, Partners, Resellers).** Following Atlassian's model, a customer-org admin should be able to:
  - see which web-agent MCP servers their people have connected, from which AI clients (Claude, ChatGPT and others, identified by OAuth client or `clientInfo`) and when
  - disconnect a person or the whole org (revoke grants), and restrict which AI clients or domains may connect
  - view per-person and per-tool usage against daily limits and the org's share of budget
  - export an audit log (tool invoked, principal, timestamp, server version, result status, data volume), ideally in a SIEM-friendly format
  - receive notices for new versions, scope growth and deprecations

  This admin surface is separate from web-agent's own publisher admin.
- **Contracts and terms (inferences, need legal review):**
  - Exposing datasets to Partners and Resellers via MCP is a data-sharing arrangement where an AI host (Anthropic, OpenAI and others) becomes an additional processor chosen by the *end customer*. Terms should spell out that the customer's chosen AI client is outside web-agent's processing chain.
  - Resellers need sub-licensing or onward-transfer terms.
  - The terms should say which datasets each audience may receive and set retention expectations.
  - They should commit to a deprecation notice period (the spec's 12-month window is an upper reference point).
  - They should define published-version immutability and change-notification obligations, and the customer's right to audit logs.
- Because host platforms place vetting on the customer, external customers will likely ask web-agent for security questionnaires covering tool annotations, change control and incident notification. A published per-server "trust page" listing the manifest version, tools with annotations, data classes, changelog and status would answer most of that. This is an inference, not documented practice.

### Gaps
- I found **no primary sources on contract or terms clauses** specific to MCP data exposure (DPAs, reseller onward-transfer, AI-client sub-processor treatment). This needs legal input.
- I found no documentation from a B2B SaaS vendor offering a *customer-facing usage report* specifically for its MCP server, beyond Atlassian's audit-log entries.
- I did not read Atlassian's linked "Monitor Atlassian MCP server activity" and "Configure Atlassian MCP server permissions" pages, which may describe per-tool read/write controls and richer usage reporting.
